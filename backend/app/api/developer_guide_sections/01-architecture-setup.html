How a request works

An API is how the screen asks the server to do something. The server checks permission, runs the rules and returns a result.

Details and source links

Every feature crosses the same boundary: the browser collects intent, FastAPI decides what is allowed, and a store or integration carries out the work. A screen never writes directly to PostgreSQL, HAPI, or an insurer.

LayerCode or serviceResponsibility
Browserfeatures/application/AppShell.tsx, features/<workflow>/, services/api/Navigation, forms, display state, typed request adapters; same-origin session cookies.
HTTPapi/application.py, api/routers/, Pydantic schemasRoute matching, input validation, authorization, response shaping.
Rulesdomain/fhir/, ingestion/, insurance/, reports/FHIR conversion, EHR/PDF input, payer interpretation, estimates, clinical reports.
Persistencecore/*_store.py, insurance/store.py, HAPI, S3/DriveAccounts, cases, event history, structured resources, original file bytes.

Run it on your computer

Use three pieces: a database, the Python API and the React website. Start the database first, then keep the API and website running in separate terminals.

Before you start: get repository access and use an ignored local .env. The commands below target Ubuntu or Ubuntu in WSL2; they identify macOS alternatives.

Details and source links

Start here on a new computer. Commands use Bash on Ubuntu 24.04 or Ubuntu in WSL2. On Windows, install WSL2 and enable Docker Desktop’s WSL integration; run the commands inside Ubuntu, not PowerShell. On macOS use Docker Desktop and the linked native installers; the apt-get commands below are Ubuntu-only. A terminal command runs in the folder shown by pwd. A new terminal needs its own cd and Python environment activation.

Native Ubuntu: Docker installation commands

Docker group membership grants powerful access to the host. Use the installation method approved for your development computer. These are Ubuntu apt-repository commands; WSL with Docker Desktop uses Desktop’s integration instead.

3. Start the database and create the application database
# Application root; Docker must already be running.
docker compose up -d postgres
docker compose exec postgres pg_isready -U hapi -d hapi

# Run once on a new local database. Wait for "accepting connections" first.
docker compose exec postgres createdb -U hapi clinicforce

docker compose up -d fhir
docker compose ps
curl --fail --silent --show-error --output /dev/null   http://localhost:8080/fhir/metadata

Compose creates a PostgreSQL 15 container and its hapi database. The extra clinicforce database above holds application accounts and cases; both use the Compose role for this local-only recipe. If createdb says the database already exists, keep it and continue. The backend creates its application tables through store initialization; there is no separate Alembic migration command in this repository. HAPI can take several minutes to initialize. Inspect docker compose logs --tail=80 fhir if its metadata endpoint is not ready. The local Compose image uses hapiproject/hapi:latest; this is not a reproduction of a pinned production image. Use staging for release verification.

4. Create an ignored local configuration and administrator

Run this from the application root with the virtual environment active. It creates a new root .env, reads the local database password from Compose without printing it, and prompts for a local-only staff password (at least 12 characters). It refuses to overwrite an existing file. If you already have a .env, edit it privately using this key list; do not replace existing configuration blindly. The password is stored as a one-way hash. Use only synthetic data in this local setup.

umask 077
python - <<'PYENV'

from pathlib import Path
from urllib.parse import quote
from passlib.hash import pbkdf2_sha256

if path.exists():
    raise SystemExit(".env already exists; review and update it privately.")

db = config["services"]["postgres"]["environment"]

Important: backend/app/__init__.py currently loads backend/.env implicitly, despite its “repository .env” comment. The startup command below explicitly loads the root file with --env-file .env. Already-exported shell variables take precedence; use a clean development terminal without production integration variables or AWS credentials. Avoid keeping a second conflicting backend/.env. Nothing secret belongs in frontend/.env or a VITE_* variable: frontend build values are delivered to browsers.

5. Run the API and frontend in separate terminals
# Terminal A — leave this running.
cd ~/clinicforce-workspace/clinicforce
source .venv/bin/activate
python -m uvicorn app.main:app --app-dir backend --env-file .env   --host 127.0.0.1 --port 8000 --reload
# Terminal B — leave this running.
cd ~/clinicforce-workspace/clinicforce/frontend
nvm use 24.11.0
npm ci
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort

Open http://localhost:5173, choose the clinic/staff sign-in screen, and use local-admin@clinicforce.invalid with the password you entered. Use localhost consistently in the browser; 127.0.0.1 is a different origin. Vite forwards /api and /manifest to FastAPI at port 8000, so the browser uses one origin and keeps its staff cookie. --strictPort prevents Vite silently moving to a port that the backend would reject. Staff bootstrap creates the administrator on first login and does not reset an existing account when the variable changes.

# Terminal C — application root.
curl --fail http://localhost:8000/healthz
curl --fail http://localhost:8000/readyz
curl --fail --silent --show-error --output /dev/null http://localhost:8000/api/docs
curl --fail --silent --show-error --output /dev/null http://localhost:8000/api/openapi.json

Expected: the health endpoints return HTTP 200; /healthz returns {"status":"ok"}. Read the local guide at port 8000 /api/docs or through Vite at port 5173. Health checks prove process/database readiness only. This minimal setup can exercise staff sign-in and basic screens; card/file storage needs S3, PDF extraction may need Bedrock, and real eCW/Stedi requests need the independent setup below. An unconfigured eCW lookup returning 503 is expected here and is not an end-to-end pass.

The database persists under the ignored postgres-data/ directory. stop preserves it; do not delete that directory as a routine restart. HAPI resources, local users and application cases survive. For database integration checks, create a disposable stafftest database and set STAFF_TEST_DATABASE_URL to that database only; tests can clear tables. Never point tests at clinicforce, staging RDS, or production RDS. CI creates its own test PostgreSQL service automatically. See .github/workflows/deploy.yml for the exact release checks.
