Locate a stalled eCW lookup

Under the same request ID, ecw_stage_started, ecw_stage_completed, and ecw_stage_failed describe metadata discovery, KMS assertion signing, token exchange, resource searches, and direct resource reads. Each event includes elapsed milliseconds, and an upstream HTTP status when one arrived. Resource requests include a fixed resource label, query shape such as given_family_birthdate (never values), page number, and returned count. Patient matching and appointment filtering record counts without identifiers. Failure codes distinguish connection/read/write/pool timeouts, upstream HTTP errors, invalid responses, resource denial, and cancellation. Token exchange can also report an allowlisted oauth_invalid_scope, oauth_unauthorized_client, or related standard OAuth code when eCW provides it; raw error descriptions and response bodies remain excluded. QR sharing: CloudFront edge logs and backend correlation

Start with the UTC time and X-ClinicForce-Request-ID response header from generation or manifest retrieval. CloudFront's X-Amz-Cf-Id identifies the edge request; the backend copies that value into cloudfront_request_id. These are different IDs. Each HTTP call gets its own IDs; they do not join generation and a later scan automatically, and they are not patient/share identifiers.

Edge destination. CloudFront standard logging v2 delivers JSON to clinicforce-staging-cloudfront or clinicforce-production-cloudfront in CloudWatch Logs, us-east-1, with 30-day retention. The infrastructure output CloudFrontLogGroupName identifies the destination. Logging covers the distribution; filter the static cache pattern /manifest/* for QR retrieval. /api/* includes generation and other API calls and cannot identify generation alone at the edge.

The selected edge fields are date/time, edge location, HTTP method/status, edge request ID, result/response/detailed-result types, total time, first-byte time and cache-behavior path pattern. URI paths, query strings, cookies, referrers, user agents, client IPs, headers and bodies are excluded. In particular, the manifest token is a secret capability and must never be added as cs-uri-stem. QR fragments and encryption keys are not HTTP request targets.

AWS: where the app runs

AWS hosts the website, API, database and files. Staging is the rehearsal environment; production is the patient and clinic site.

This describes the checked-in design. Inspect AWS for the current deployed version and status.

Think of AWS as the building

Route 53 is the address book, CloudFront the front door, ALB the receptionist, and ECS the workers. This analogy explains routing, not the security controls.

Two separate copies

Staging is the rehearsal site; production is the real site. Each has its own network, database, files, keys, services and logs in the same AWS account.

Records and files differ

RDS stores structured rows. Private S3 holds original documents and raw evidence. HAPI keeps FHIR records in the same RDS instance, in its own tables.

A green server is not a green workflow

Health checks show that processes respond. They do not prove that an eCW read, payer check, email or AI request succeeded.

How AWS Bedrock helps suggest CPT codes

CPT is the code used to describe a planned or performed service. ClinicForce uses Amazon Bedrock as a coding assistant while preparing some visit estimates. Bedrock proposes a provisional plan; it does not decide what was performed, what the insurer covers, or what the clinic may collect.

What is sent: depending on the workflow, the Bedrock request can contain the current appointment reason or entered clinical text, visit type, up to ten recent completed visits with their dates/reasons/coded services, a bounded list of CPT codes and descriptions, and relevant planning options. The fee-schedule suggestion path sends candidate codes and descriptions rather than the entire uploaded CSV. The visit-plan path may also include clinic cash-package planning data. These fields can contain patient-specific clinical context, so they stay in the server-to-AWS request and must not be copied into logs or public examples. This CPT call is separate from the Bedrock PDF-extraction path and from payer requests to Stedi or Availity.

When it runs: a fresh documented appointment may request preliminary, unpriced candidate codes; a case with an uploaded clinic fee schedule can ask for suggestions constrained to that schedule; the commercial visit planner can ask for one editable cost scenario when an explicit scheduled service does not already settle the plan. A matching saved visit context can reuse its suggestions. Some clear scheduled or rule-based cases do not need a model call.

What happens next: the fee-schedule path rejects codes outside the uploaded schedule. The visit-plan path checks code membership, units, mutually exclusive nerve-study levels, EMG companion rules, visit status and scheduled-service precedence; an invalid proposal may be retried once. If Bedrock is unavailable, the path may show conservative fee-description matches, a supported historical/provisional scenario, or an unavailable state with a retry. The model never supplies a payer-confirmed allowance or final billing decision. Final coding follows the care documented by the clinician.

The ECS backend role permits bedrock:InvokeModel for the configured US inference profile and its routed model ARNs; each model call can add usage cost. See cpt_suggester.py, cpt_rules.py, and the insurance workflow guide for the exact planning rules. The AWS template defines the model setting and IAM permission.

Why PostgreSQL on RDS instead of DynamoDB?

Short answer: ClinicForce's current records are related to each other, and both the application and HAPI use PostgreSQL. RDS is AWS's managed way to run that database. DynamoDB is a different kind of database, not a drop-in replacement for the SQL these services already use.

In plain language, SQL lets ClinicForce ask “show this practice's cases with their intake and patient” and update a case without two workers overwriting each other. The current code uses joins, PostgreSQL JSONB fields, transactions, FOR UPDATE row locks and revision checks. HAPI is configured for PostgreSQL through JDBC. Switching only the AWS resource name to DynamoDB would break those queries and HAPI storage; it would require redesigning the data model, access paths, concurrency rules and FHIR storage. DynamoDB can be useful for other access patterns, but this codebase does not use it.

RDS also brings database backups, encryption, a private network endpoint and managed database operations. It has an always-running instance and needs capacity/maintenance planning. This is an explanation of the present design based on the code and template, not a claim that DynamoDB was benchmarked and rejected. See the data-store decision, insurance/store.py and the RDS/HAPI task settings.

The Lambda function: when it runs and why

There is one Lambda function in the shared ClinicForce AWS stack: SecretRotationDeploymentFunction, created separately for staging and production. A Lambda function is a short piece of code AWS runs for an event; it is not one of the always-running application containers.

The function does not rotate the password itself, read patient records, process PDF uploads, make CPT suggestions or run on each website request. Its job is to refresh two services because ECS-injected secrets are read when a task starts. It is limited to the named environment's cluster and services. Rotating an unrelated provider secret does not trigger this rule. Check the EventBridge event, Lambda invocation and ECS rollout if a database-secret change leaves tasks using an old password. See the function and event rule in the template.

What AWS does with uploaded PDFs—and what “summary” means here

Correction: ClinicForce does use AWS Bedrock while importing some patient health PDFs, but the model extracts source-backed clinical facts rather than writing the clinician's finished summary. A separate, deterministic backend function later assembles the clinician narrative from saved FHIR records.

What leaves the backend for Bedrock: PDF page text (capped at 8,000 characters per text page) or a rendered PNG for a page with no extractable text, plus page numbers and extraction instructions. The original PDF bytes are not sent as one PDF object in this model call. The upload endpoint caps each PDF at 15 MB. Bedrock can receive sensitive clinical content, so the call uses the backend task's AWS role and is not made from the browser. The model is told to use only visible facts and avoid guessing; its JSON is checked against a strict schema before ClinicForce creates FHIR resources. A page citation identifies the original file and page for review, but it is not a guarantee that every fact is clinically correct.

Failure and limits: no supported facts yields a 422 upload result; invalid or unavailable extraction fails the import rather than inventing a normal summary. The backend limits each Bedrock response to a bounded number of output tokens and facts. Long text can be truncated per page, so an operator should review the original source when completeness matters. Original file storage and FHIR storage are separate steps with their own failure handling. The finished clinician summary is generated from saved FHIR data by reports/summarizer.py; the extraction path is bedrock_extractor.py and import_routes.py. Neither stage uses the secret-rotation Lambda.

Where personal data goes, and what protects each boundary

The browser talks to CloudFront over HTTPS. The current template sends CloudFront-to-ALB traffic over HTTP, then ALB-to-backend and backend-to-HAPI over HTTP inside the VPC. RDS clients request TLS. The document bucket denies non-HTTPS S3 access. Do not mistake restricted network entry for encryption on every internal hop.

CloudFront can read the static bucket through Origin Access Control. The backend task role can read and write only its allowed document prefix and call configured KMS, Textract, Bedrock and optional SES actions. HAPI has database access but no document-bucket permission in this template. The RDS instance is private; the two ECS tasks are in public subnets with public IPs, but security groups allow only the specified inbound peers. Application session and practice checks still matter after network checks.

RDS backup retention is seven days, and deletion/replacement takes a snapshot. Document-bucket versioning is on; noncurrent versions expire after seven days. The clinicforce/insurance-cases/ prefix has a one-day lifecycle; durable clinic evidence uses a different prefix. An application deletion, an object lifecycle rule, an RDS backup, and a release rollback are different operations. Optional patient-owned Google Drive files are stored outside AWS, although ClinicForce keeps encrypted token metadata in RDS.

See the data ownership section for which record lives where, safe inspection for operator access, and the technical inventory for exact template settings.

How changes go live, how to spot failure, and what costs money

If the site name does not resolve, start at Route 53. A browser certificate error points to ACM/CloudFront. Missing HTML or JavaScript points to CloudFront/static S3. An API 5xx points through CloudFront, ALB, ECS and backend logs. A ready API with failed saves points to RDS or S3. A failed FHIR read may involve HAPI or an external eCW call; those are different paths. Use the request support reference in CloudWatch troubleshooting. CloudFormation events explain resource updates; ECS events explain unhealthy task rollouts; GitHub Actions explains builds and publication.

The main recurring AWS cost drivers are the always-running RDS, ALB and two Fargate tasks in each environment, plus CloudFront traffic, S3 storage/requests, logs, KMS requests and ECR storage. Textract, Bedrock and SES add usage-based charges when their features run; outside providers may bill separately. The template contains no budget or price estimate. Check AWS billing for actual spend and service pricing for any forecast.

  1. Describe the actor, entry screen, permission, input, saved state, failure state, and next action before adding a route or table.
  2. Use an existing intake or case when its scope and lifecycle fit; introduce a table for a distinct access rule, version, query, or retention need. Keep original bytes out of application rows.
  3. Change a Pydantic model and its TypeScript adapter together. Add a focused test for the authorization or state transition that matters.
  4. Release to staging, verify the affected workflow, and explicitly promote its successful Actions run. Production uses the same image digests and frontend files; it preserves unrelated stack parameters. A failing provider workflow blocks promotion even when health checks pass.

Do not infer a live integration from a route alone. An earlier October 3 deployment inspection found Availity's environment was demo, ID.me was enabled in sandbox, and the Stedi commercial pilot switches were on. The production template source can differ from the currently deployed template if its last infrastructure update rolled back.

Staging and production releases

The release pipeline uses clinicforce-staging at https://staging.clinicforce.ai and clinicforce-production at https://app.clinicforce.ai. Each stack owns its VPC, ECS services, RDS database, document and static buckets, keys, secrets, and log groups. Staging starts empty with a synthetic QA staff account. Its PostgreSQL 18.3 database uses db.t4g.small because the existing production db.t4g.micro size was unavailable for new instances in the region at setup; production sizing is preserved. Never copy production databases, documents, patient identities, or provider credentials into staging. Its Stedi fixture mode makes no paid eligibility requests; eCW is unconfigured until a separately authorized test connection exists.

Pull requests run backend tests, deidentified saved UHC response projections through the rendered staff estimate screen, frontend checks (including upcoming and completed eCW visit-date grouping), and secret scanning. The UHC projection test uses the same three backend fixtures as the insurance regression tests and checks that returned payer evidence, exact collection instructions, and clinic-approved deferral render together. A main-branch application release builds once, records backend and HAPI digests, stores the frontend artifact for 90 days, then deploys staging and checks public routes, this guide, the API reference, and synthetic staff sign-in/session/logout, Swagger session recognition, matching clinician execution and wrong-role rejection. Production is a manual promotion of that successful staging run. The verification reference is an operator attestation of successful representative workflow checks; basic smoke tests do not certify appointment lookup, eligibility, OAuth provider access, or every browser journey. An unresolved affected workflow blocks release. No automatic emergency bypass is provided.

The command prints the Actions URL, follows job status and reports failure logs. With local AWS credentials it also prints CloudFormation events and ECS desired/running/pending counts; those progress records always appear in the Actions release step. Docker uses plain build progress. Application request logs stay in CloudWatch and are not copied into CI output. A failed wait or rolled-back image prevents frontend publication. A smoke failure after publication marks the release failed; it does not automatically undo database or application changes. Re-promote a compatible prior successful staging run only after verifying it against the current schema. Retain its ECR digests; expired Actions artifacts cannot be promoted.

Infrastructure parameters live in clinicforce-aws/environments/staging.json and production.json. Omitted production parameters retain their deployed values. Keep secrets in Secrets Manager; commit only public settings and approved secret ARNs. Production compares the template and parameter file to the successful staging artifact. The two repositories have separate queues; CloudFormation rejects conflicting updates, so finish infrastructure before releasing the application. Inspect AWS before retrying a timed-out command because the server operation may continue.

One-time setup uses python3 scripts/bootstrap_staging.py in the infrastructure repository with an operator AWS identity and GitHub environment/secret permissions. It prepares the application's staging GitHub environment (the infrastructure workflow creates its own environment on first use), stores a generated QA password only in that environment secret, and provisions isolated AWS resources using the currently running image digests. Then merge the staging-first workflows and release the application to install this guide and run smoke tests. The first production infrastructure update requires an operator identity because the existing deploy role cannot modify its own policy; see the infrastructure README. Application release refuses to change a stack until that environment-aware template is installed. This setup creates additional always-on AWS resources. GitHub environment approval and branch protection were unavailable on the current private-repository plan when inspected; workflow conditions and explicit promotion enforce the release procedure, but do not replace platform protection against a repository administrator changing that procedure.

Where everything lives, and why

The authoritative topology is stacks/clinicforce-production.yaml. Despite its filename, this shared template creates both environments using EnvironmentName. The legacy stacks/ecs-backend.yaml and stacks/ecs-hapi.yaml are not the routine release targets. The inventory below describes the checked-in template; inspect stack outputs and running ECS task definitions for the current deployed identities.

Keep the live guide current

Every new capability or change to a screen, workflow, API contract, data model, integration, infrastructure, deployment, or operational behavior must update the relevant section of this guide in the same release. Put the explanation where a reader would look for that topic, including setup, failure states, and operational checks when they matter. API contract changes also require accurate FastAPI route and model descriptions in the generated reference below. The guide source is backend/app/api/developer_docs.html; its OpenAPI grouping lives in backend/app/api/developer_docs.py. Infrastructure changes are documented here through a coordinated application release. Check the affected guide section and Swagger reference after deployment. Keep patient data and secrets out of examples.
