Find why a request failed

Capture the request ID, identify the first failing stage and follow it into the logs. A timeout does not prove that a patient or appointment is absent.

Use synthetic cases to practice. Keep patient details, raw payloads and credentials out of logs, screenshots and shared notes.

Trace an arrival estimate in CloudWatch

For eCW lookup, commercial appointment listing, intake identity confirmation, and commercial previsit requests, copy the X-ClinicForce-Request-ID response header. Search that ID in CloudWatch log group /ecs/clinicforce-production-backend to join structured JSON events for the request. Events record stages, outcome and reason codes, opaque practice/intake/case identifiers, timing, and calculated amount in cents where applicable. A deferred or unavailable result must be investigated through its reason code and case evidence; it does not imply a payer supplied a price. The events deliberately omit names, dates of birth, request and response bodies, credentials, and raw payer data.

For automatic coverage recovery, filter coverage_recovery events by case/request ID. Stages distinguish card/OCR, payer routing, discovery, candidate matching, eligibility and pricing. Fixed reasons distinguish no coverage returned, multiple active policies, identity/date mismatch, enrollment prerequisites, prior-address retries, timeouts and unavailable rates/benefits. See coverage recovery; private response evidence supplies the patient-specific details.

ecw_insurance_resolution separately records patient-bound Coverage count, appointment-note candidate count and subscriber availability. coverage_recovery stages discovery_result and candidate_filter separate raw upstream items from accepted candidates; upstream_no_policies differs from all_candidates_filtered. discovery_cache records reuse without a new submission. card_precheck records the first-request card comparison outcome and file count without extracted values; card_download and card_ocr record later recovery read and OCR completion. Scope grants and a successful empty document search do not prove insurance cards are absent from the EHR screen. Card-list calls from the staff screen have their own request IDs; join their intake URL to the estimate intake before attributing an OCR attempt. Historical logs contain opaque intake/case IDs, not patient accounts or appointment payloads: exact account-to-trace attribution requires the authorized saved intake/case record or the browser support reference. Never infer that link from adjacent timestamps alone.

Locate a stalled eCW lookup

Under the same request ID, ecw_stage_started, ecw_stage_completed, and ecw_stage_failed describe metadata discovery, KMS assertion signing, token exchange, resource searches, and direct resource reads. Each event includes elapsed milliseconds, and an upstream HTTP status when one arrived. Resource requests include a fixed resource label, query shape such as given_family_birthdate (never values), page number, and returned count. Patient matching and appointment filtering record counts without identifiers. Failure codes distinguish connection/read/write/pool timeouts, upstream HTTP errors, invalid responses, resource denial, and cancellation. A cancellation followed by ecw_lookup_deadline means ClinicForce cancelled the in-flight stage at its overall budget; it is not an upstream HTTP 504. A missing upstream status means no complete HTTP response was available to the client. Commercial appointment-list requests also emit collection_http_completed, so their support references can be searched even when the reader fails.

fields @timestamp, event, stage, resource, query_kind, page, http_status, reason_code, duration_ms, count
| filter request_id = "SYNTHETIC-REQUEST-ID"
| sort @timestamp asc

To isolate a regression, compare the deployed eCW issuer/client/signing-key configuration and request shape with the last successful image. A diagnostic read may inspect a redacted FHIR OperationOutcome privately; never put raw response bodies, URLs, query values, bearer tokens, session cookies, or exception strings in application logs or this guide. A failure before patient and visit resolution prevents the Stedi estimate path from starting.

CloudWatch from the beginning

CloudWatch is AWS’s log viewer. A log group is the environment/service collection; a log stream belongs to a task/container instance. Deployments replace tasks and create new streams, so search the group rather than only the newest stream. GitHub Actions logs explain build/deployment progress; CloudFormation events explain resource changes; ECS events explain task restarts; application logs explain requests. CloudTrail is the audit of AWS API calls (such as KMS Sign), not an eCW response-body log.

QR sharing: CloudFront edge logs and backend correlation

Start with the UTC time and X-ClinicForce-Request-ID response header from generation or manifest retrieval. CloudFront's X-Amz-Cf-Id identifies the edge request; the backend copies that value into cloudfront_request_id. These are different IDs. Each HTTP call gets its own IDs; they do not join generation and a later scan automatically, and they are not patient/share identifiers.

Edge destination. CloudFront standard logging v2 delivers JSON to clinicforce-staging-cloudfront or clinicforce-production-cloudfront in CloudWatch Logs, us-east-1, with 30-day retention. The infrastructure output CloudFrontLogGroupName identifies the destination. Logging covers the distribution; filter the static cache pattern /manifest/* for QR retrieval. /api/* includes generation and other API calls and cannot identify generation alone at the edge.

The selected edge fields are date/time, edge location, HTTP method/status, edge request ID, result/response/detailed-result types, total time, first-byte time and cache-behavior path pattern. URI paths, query strings, cookies, referrers, user agents, client IPs, headers and bodies are excluded. In particular, the manifest token is a secret capability and must never be added as cs-uri-stem. QR fragments and encryption keys are not HTTP request targets.

// Logs Insights: select the environment's CloudFront group
fields @timestamp, `cs-method`, `sc-status`, `x-edge-request-id`,
       `x-edge-result-type`, `x-edge-detailed-result-type`, `time-taken`
| filter `cache-behavior-path-pattern` = "/manifest/*"
| sort @timestamp desc
| limit 100

Backend destination. Select /ecs/clinicforce-staging-backend or /ecs/clinicforce-production-backend. Structured sharing_http_completed events use stages share_create, manifest_fetch and share_summary, recording status, duration, outcome, request ID and edge ID when present. Validation failures are captured even if the route body never runs. sharing_http_failed means an unhandled exception before a normal response. Sharing responses include Cache-Control: no-store. Access logs redact the manifest path token and query.

fields @timestamp, event, stage, request_id, cloudfront_request_id,
       http_status, outcome, duration_ms
| filter event in ["sharing_http_completed", "sharing_http_failed"]
| sort @timestamp desc
| limit 100

// To join one edge request, add this filter to the backend query:
// | filter cloudfront_request_id = "EDGE_REQUEST_ID_FROM_CLOUDFRONT"

The existing Secure Sharing messages additionally identify successful creation mode, manifest attempt, invalid PIN, unavailable share and lifetime PIN lockout. They do not carry a durable share-to-import receipt. No QR key, PIN, patient values, recipient label, encrypted payload, manifest token or download URL belongs in these diagnostics.

Timing and limits. Standard logs are asynchronous and best effort. AWS documents that configuration changes can take up to 12 hours. Wait for actual delivered test events before declaring edge logging verified; an enabled setting or empty immediate query is insufficient. An S3 download and the receiver's chart write are separate from a manifest 200. This configuration does not add S3 object-access auditing or vendor mobile logs. New logging is not retroactive. Charges follow CloudWatch vended-log ingestion, storage and query usage.

Staging and production releases

The release pipeline uses clinicforce-staging at https://staging.clinicforce.ai and clinicforce-production at https://app.clinicforce.ai. Each stack owns its VPC, ECS services, RDS database, document and static buckets, keys, secrets, and log groups. Staging starts empty with a synthetic QA staff account. Its PostgreSQL 18.3 database uses db.t4g.small because the existing production db.t4g.micro size was unavailable for new instances in the region at setup; production sizing is preserved. Never copy production databases, documents, patient identities, or provider credentials into staging. Its Stedi fixture mode makes no paid eligibility requests; eCW is unconfigured until a separately authorized test connection exists.

Pull requests run tests and secret scanning. A main-branch application release builds once, records backend and HAPI digests, stores the frontend artifact for 90 days, then deploys staging and checks public routes, this guide, the API reference, and synthetic staff sign-in/session/logout, Swagger session recognition, matching clinician execution and wrong-role rejection. Production is a manual promotion of that successful staging run. The verification reference is an operator attestation of successful representative workflow checks; basic smoke tests do not certify appointment lookup, eligibility, OAuth provider access, or every browser journey. An unresolved affected workflow blocks release. No automatic emergency bypass is provided.

GitHub environment approval and branch protection were unavailable on the current private-repository plan when inspected; workflow conditions and explicit promotion enforce the release procedure, but do not replace platform protection against a repository administrator changing that procedure.
