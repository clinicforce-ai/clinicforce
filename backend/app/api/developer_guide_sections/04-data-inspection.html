Look at tables and files

Start with a local test database. Use a SQL client for rows and S3 tools for files. The AWS console login, app login and database login are separate.

Cloud RDS is private. This stack does not create an operator tunnel or read-only SQL account. Follow the access prerequisites below; do not make the database public.

Details and source links

Use this section when you want to see what the application actually saved. PostgreSQL stores rows and relationships; S3 stores files addressed by object keys. AWS RDS manages the PostgreSQL server. The RDS console shows the server, connectivity and monitoring; use a PostgreSQL client to browse this instance’s tables and execute SQL. An AWS console login, a ClinicForce staff login, and a PostgreSQL login are three different credentials.

Current access boundary: the checked-in stack makes RDS private and allows PostgreSQL traffic only from the backend/HAPI security groups. It provisions no operator VPN, SSM jump host, SQL browser, or read-only database login, and does not enable ECS Exec. The RDS instructions below require an operator-provisioned access path and database role first. They document how to use that access; publishing this guide does not create it. Do not turn on public RDS access to make a desktop client connect.

1. Start with the local database

Complete local setup, including starting the backend and signing in once so the relevant stores initialize their tables. From the application repository, open the PostgreSQL terminal supplied by Compose:

docker compose ps
# Opens an interactive SQL prompt in your local application database.
docker compose exec -e PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=10000' postgres psql -X -U hapi -d clinicforce

Commands starting with a backslash below are psql commands, not Bash. SQL statements end with a semicolon. \d describes columns and indexes; it does not display rows. Press q to leave the pager, or turn it off as shown.

\conninfo
\pset pager off
\dt public.*
\d public.staff_patients
\d public.staff_intakes
SHOW transaction_read_only;
SELECT current_database(), current_user;
-- Continue with the SQL examples in step 5, then exit:
\q

Local HAPI uses a separate hapi database. To inspect its table names use docker compose exec postgres psql -X -U hapi -d hapi, then \dt public.*. In AWS, both the application and HAPI use the clinicforce database. Browse HAPI table metadata to understand storage; change clinical resources through its FHIR API, not hand-written HAPI SQL updates.

2. Locate the correct AWS database and buckets

In the AWS console select us-east-1. Open CloudFormation → clinicforce-staging → Resources → Database to find the RDS instance. In RDS, its Connectivity & security tab shows its endpoint, port and security groups. CloudFormation’s Outputs tab gives DocumentsBucketName and StaticBucketName. Do not guess generated resource names. For production, deliberately choose clinicforce-production.

For the CLI, use the AWS profile your operator assigned. The example profile name is a placeholder. If your organization uses IAM Identity Center, configure it once with aws configure sso --profile clinicforce-operator and sign in with aws sso login --profile clinicforce-operator. Otherwise use the organization’s existing credential method. Installing the CLI alone does not grant access.

export AWS_PROFILE=clinicforce-operator
export AWS_DEFAULT_REGION=us-east-1
export AWS_PAGER=''
aws sts get-caller-identity

# Start in staging. Re-run discovery after deliberately changing environments.
export CF_STACK=clinicforce-staging
CF_DB_ID=$(aws cloudformation describe-stack-resource   --stack-name "$CF_STACK" --logical-resource-id Database   --query 'StackResourceDetail.PhysicalResourceId' --output text)
export CF_DB_HOST=$(aws rds describe-db-instances   --db-instance-identifier "$CF_DB_ID"   --query 'DBInstances[0].Endpoint.Address' --output text)
aws rds describe-db-instances --db-instance-identifier "$CF_DB_ID"   --query 'DBInstances[0].{ID:DBInstanceIdentifier,Engine:Engine,Version:EngineVersion,Database:DBName,Host:Endpoint.Address,Port:Endpoint.Port,Public:PubliclyAccessible}'
export CF_DOCUMENT_BUCKET=$(aws cloudformation describe-stacks   --stack-name "$CF_STACK"   --query "Stacks[0].Outputs[?OutputKey=='DocumentsBucketName'].OutputValue | [0]" --output text)
export CF_STATIC_BUCKET=$(aws cloudformation describe-stacks   --stack-name "$CF_STACK"   --query "Stacks[0].Outputs[?OutputKey=='StaticBucketName'].OutputValue | [0]" --output text)

These commands read resource metadata, not database rows or secret values. Expected database: clinicforce, port 5432, Public: false. The host and bucket variables apply to this terminal only. A missing value or AccessDenied means stop and resolve the profile/resource permissions; it is not evidence that the database is empty.

3. Establish private RDS access

The operator must provide both network access and database permission. A supported approach is an SSM-managed EC2 jump host in the selected environment’s VPC: it needs DNS/routing to RDS, SSM Agent 3.1.1374.0 or newer, an SSM instance role, and HTTPS access to Systems Manager through endpoints or outbound connectivity. Add a dedicated jump-host security group and allow it to reach RDS on 5432 through a reviewed infrastructure change. No public SSH port is needed. Alternatively use an approved VPN with database routing and security-group access. Neither is included in the current stack.

On your computer install the Session Manager plugin and a PostgreSQL client. Prefer a client matching or newer than the server’s major version for catalog commands. On Ubuntu, sudo apt-get install postgresql-client supplies the distribution’s client; check psql --version against the RDS version above. The operator’s AWS role needs ssm:StartSession scoped to the approved managed node and remote-host forwarding document, and permissions to resume/terminate its own sessions.

# Terminal A: keep the discovered CF_DB_HOST and AWS profile from step 2.
session-manager-plugin --version
psql --version
# Replace this placeholder with the operator-provided managed EC2 instance.
export CF_SSM_TARGET=i-REPLACE_WITH_APPROVED_INSTANCE
aws ssm start-session --target "$CF_SSM_TARGET"   --document-name AWS-StartPortForwardingSessionToRemoteHost   --parameters "host=$CF_DB_HOST,portNumber=5432,localPortNumber=15432"

Leave terminal A running. It forwards your local port 15432 to the private database through the managed host. In terminal B, repeat the profile and database-discovery commands from step 2, then connect below. SSM authorization does not log you into PostgreSQL. See AWS’s remote-host port forwarding instructions and worked networking example.

4. Use a separate database reader account

Ask the database administrator for an individual read-only PostgreSQL login and its approved table/view scope. This is independent of your AWS role and ClinicForce account. The deployed application uses the clinicforce master role with an RDS-managed password injected into its tasks; do not copy that application credential into the guide, Git, a command argument, or your SQL client configuration. Deliver the reader password through the approved private credential channel.

Administrator-only example: provision a reader for selected tables

This block changes database permissions and must be run by the DBA over an authorized connection, after these tables exist. It is a template for a new login, not a routine inspection command. Substitute an individual role name and approve the table list. \password prompts without placing the password in the SQL text.

CREATE ROLE clinicforce_reader LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
\password clinicforce_reader
GRANT CONNECT ON DATABASE clinicforce TO clinicforce_reader;
GRANT USAGE ON SCHEMA public TO clinicforce_reader;
GRANT SELECT ON public.staff_patients, public.staff_intakes,
  public.insurance_cases, public.insurance_case_events,
  public.patient_documents, public.commercial_rate_versions,
  public.commercial_rate_lines TO clinicforce_reader;
ALTER ROLE clinicforce_reader SET default_transaction_read_only = on;
ALTER ROLE clinicforce_reader SET statement_timeout = '10s';

The listed grants expose all rows and columns of those tables, including patient information. They do not enforce clinic isolation: a WHERE practice_id = ... clause is a query filter, not an access boundary. For clinic-limited access, the DBA must instead grant approved restricted views or implement reviewed row-level policies. Check effective inherited/PUBLIC permissions and callable functions before issuing the login. Read-only defaults reduce mistakes; SELECT-only permissions are the main restriction. Do not grant all tables, all future tables, session/token tables, or master-role membership merely to make a missing-table error disappear.

# Terminal B: CF_DB_HOST must be the actual RDS DNS endpoint from step 2.
mkdir -p "$HOME/.postgresql"
curl --fail --silent --show-error   https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem   -o "$HOME/.postgresql/rds-global-bundle.pem"
export CF_DB_USER=clinicforce_reader
PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=10000 -c lock_timeout=2000' PSQL_HISTORY=/dev/null psql -X -W "host=$CF_DB_HOST hostaddr=127.0.0.1 port=15432 dbname=clinicforce user=$CF_DB_USER sslmode=verify-full sslrootcert=$HOME/.postgresql/rds-global-bundle.pem connect_timeout=10"

Enter the reader password at the prompt. hostaddr sends traffic through the local tunnel while host retains the real RDS name for certificate verification. Keep sslmode=verify-full; changing it to disable encryption is not a connection fix. With an approved direct VPN connection, omit hostaddr=127.0.0.1 and use port 5432. Learn PostgreSQL connection parameters and RDS certificate bundles.

5. List tables, inspect columns, and query rows

Run these inside psql, either locally or through the RDS connection. Start by checking where you connected. Use BEGIN READ ONLY and end with ROLLBACK; this avoids leaving a transaction open while you browse. If a query errors, run ROLLBACK; before starting another transaction.

\conninfo
\pset pager off
SELECT current_database(), current_user;
SHOW transaction_read_only;
BEGIN READ ONLY;
-- Lists tables/views visible to your database role.
SELECT table_schema, table_name, table_type
FROM information_schema.tables
WHERE table_schema = 'public'
ORDER BY table_name;

-- Inspect one table without reading its patient values.
SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'staff_intakes'
ORDER BY ordinal_position;
ROLLBACK;

Now query data. These examples use the synthetic practice release-qa (local-demo for the local recipe). Replace it only with a practice you are authorized to inspect. Empty results mean no visible matching rows; staging is not a copy of production. LIMIT 20 limits returned rows, while the timeout bounds execution time.

\set practice_id 'release-qa'
BEGIN READ ONLY;
-- A small patient grid: actual values, displayed only in your private SQL client.
SELECT id, given_name, family_name, birth_date, identity_status, created_at
FROM public.staff_patients
WHERE practice_id = :'practice_id'
ORDER BY created_at DESC, id
LIMIT 20;

-- Intake status counts, without expanding patient or OCR JSON.
SELECT status, count(*) AS intake_count
FROM public.staff_intakes
WHERE practice_id = :'practice_id'
GROUP BY status ORDER BY status;

-- Follow intake -> insurance case; these rows do not prove payer success.
SELECT i.id AS intake_id, i.status, c.id AS case_id, c.created_at
FROM public.staff_intakes AS i
LEFT JOIN public.insurance_cases AS c
  ON c.intake_id = i.id AND c.practice_id = i.practice_id
WHERE i.practice_id = :'practice_id'
ORDER BY i.updated_at DESC, i.id, c.id
LIMIT 20;

-- Review saved case stages, keeping clinic scope in the join.
SELECT c.id AS case_id, e.stage, e.created_at
FROM public.insurance_cases AS c
JOIN public.insurance_case_events AS e ON e.case_id = c.id
WHERE c.practice_id = :'practice_id'
ORDER BY e.created_at DESC, e.id DESC
LIMIT 20;
ROLLBACK;

For one specifically authorized row, inspect its fields, documents, or workflow_json only when needed. fields and documents are JSONB; insurance_cases.workflow_json and event snapshots are JSON stored as text. The SQL below extracts one intake’s saved document references instead of dumping the full record. The UUID is a synthetic placeholder.

\set intake_id '00000000-0000-0000-0000-000000000000'
BEGIN READ ONLY;
SELECT i.id, d.value ->> 'object_key' AS object_key,
       d.value ->> 'content_type' AS content_type
FROM public.staff_intakes AS i
CROSS JOIN LATERAL jsonb_array_elements(i.documents) AS d(value)
WHERE i.practice_id = :'practice_id' AND i.id = :'intake_id'
LIMIT 20;
ROLLBACK;
\q

Portal uploads use patient_documents.s3_key with storage_provider; a Google Drive document is not an S3 object despite that column name. Clinic library files use staff_library.object_key and need a separate SELECT grant. Read SQL in a private client; do not paste query results, patient names, raw JSON, filenames or tokens into public tickets, shared logs, screenshots, this guide, or Codex context notes. Use explicit columns rather than SELECT *. For query-plan investigation start with EXPLAIN; EXPLAIN ANALYZE actually runs the query.

6. Browse a table visually with pgAdmin

Install pgAdmin if you prefer a table grid. Register a server with a clear name such as ClinicForce staging — read only. For local Compose use host localhost, port 5432, database clinicforce, user hapi, and the local Compose password. For RDS over an approved VPN use the real endpoint, port 5432, database clinicforce, the reader login, SSL mode verify-full and the downloaded RDS CA bundle.

For the SSM tunnel, use pgAdmin’s connection parameters: host is the real RDS endpoint, hostaddr is 127.0.0.1, port is 15432, and SSL remains verify-full. Under Parameters → + → Host address, enter 127.0.0.1 (the hostaddr setting); if your client version lacks this field, use the psql recipe or the VPN connection instead of disabling certificate checks. The pgAdmin process must run on the same machine as the tunnel; a remote/web-hosted pgAdmin server has a different localhost. See the server connection dialog reference.

Expand Servers → your connection → Databases → clinicforce → Schemas → public → Tables. Select a table to see its Columns. Open Tools → Query Tool to run the SQL above. Backslash commands such as \set are psql-only: in Query Tool replace :'practice_id' with the quoted synthetic value 'release-qa' and remove the backslash lines. For a row grid, prefer a filtered SELECT with LIMIT; “View/Edit Data → First 100 Rows” is appropriate only when you are authorized to view every returned row. Keep the reader login and avoid grid-edit/save operations. Do not export production rows as development fixtures.

7. Browse S3 files and connect them to database rows

In S3 → Buckets, open the document bucket discovered in step 2, then its Objects tab. Prefixes look like folders, but an object key is the entire path. Choose an authorized object to see its size, type, encryption and versions. Download retrieves its contents to your computer. Use the approved private workspace; do not make the bucket public or create shareable presigned links for troubleshooting. The static bucket contains website assets, not clinic documents.

Your AWS role needs s3:ListBucket for the permitted bucket/prefix and s3:GetObject for the permitted objects. Downloading SSE-KMS documents additionally needs kms:Decrypt allowed by IAM and the key policy. SQL SELECT privileges do not grant any S3 access. Bucket discovery requires CloudFormation read permission; RDS discovery requires RDS describe permission.

# Run in the AWS terminal from step 2. Show only a bounded first page.
aws s3api list-objects-v2 --bucket "$CF_DOCUMENT_BUCKET"   --prefix 'clinicforce/' --delimiter '/' --max-keys 20 --no-paginate   --query '{Prefixes:CommonPrefixes[].Prefix,More:IsTruncated}'

# Use a specific approved record prefix copied from its saved object key.
# Placeholder only: replace it with that record's exact prefix.
CF_OBJECT_PREFIX='clinicforce/staff-insurance/REPLACE_PRACTICE_HASH/REPLACE_RECORD_ID/'
aws s3api list-objects-v2 --bucket "$CF_DOCUMENT_BUCKET"   --prefix "$CF_OBJECT_PREFIX" --max-keys 20 --no-paginate   --query '{Objects:Contents[].{Key:Key,Bytes:Size,Modified:LastModified},More:IsTruncated}'

# Inspect one exact object, without printing its contents or custom metadata.
read -r -p 'Exact authorized S3 object key: ' CF_OBJECT_KEY
aws s3api head-object --bucket "$CF_DOCUMENT_BUCKET" --key "$CF_OBJECT_KEY"   --query '{Bytes:ContentLength,Type:ContentType,Encryption:ServerSideEncryption,Modified:LastModified,Version:VersionId}'

More: true means the first page is incomplete, not that the bucket has only 20 objects. Narrow the prefix or use the console’s pagination. Hashed practice partitions and opaque IDs must be obtained from the saved reference; guessing patient names as S3 paths will not work. See listing and pagination and object metadata.

# Optional: download ONLY the selected authorized object to a private temp folder.
umask 077
CF_INSPECT_DIR=$(mktemp -d "${TMPDIR:-/tmp}/clinicforce-inspect.XXXXXX")
chmod 700 "$CF_INSPECT_DIR"
aws s3api get-object --bucket "$CF_DOCUMENT_BUCKET" --key "$CF_OBJECT_KEY"   "$CF_INSPECT_DIR/object.bin" --query '{Bytes:ContentLength,Type:ContentType}'
file "$CF_INSPECT_DIR/object.bin"
# Open this local file in the approved viewer for its reported type.
# After inspection, remove precisely this local copy (does not delete S3 data).
rm -i -- "$CF_INSPECT_DIR/object.bin"
rmdir -- "$CF_INSPECT_DIR"

An SSE-KMS download is decrypted by S3 for an authorized caller, so the downloaded copy needs protection. Some payloads also have application-level encryption (for example SHL JWE); downloading them does not turn them into plaintext. Prefer the authenticated application viewer for those. This recipe does not bulk-sync a bucket, change objects, or print document bodies into the terminal. Object-download documentation: GetObject.

8. Troubleshoot access and find the implementation
What you seeWhat to check
RDS connection times outCorrect environment/endpoint, tunnel running, unused local port, managed-host DNS/routes and database security-group ingress. A timeout usually precedes password authentication.
SSM target not connected / plugin missingApproved target ID, SSM Agent/instance role/outbound connectivity, local plugin and operator StartSession permissions. No jump host is currently created by this stack.
Password failed / permission denied for tableCorrect database reader login/password and explicit grants. The app staff password cannot authenticate to PostgreSQL.
Certificate name mismatchUse the actual RDS hostname for host and local loopback only for hostaddr; check the CA bundle. Do not switch SSL off.
No tables / relation does not existConfirm database and schema, role visibility, deployed version and whether the relevant app store has initialized. Do not run app schema initialization as the reader.
Read-only error / statement timeoutExpected for writes or expensive inspection queries. Narrow the query and use indexes. Do not remove read-only restrictions to inspect rows.
S3 AccessDenied / object not foundCorrect environment, bucket, exact saved key, S3 grants and KMS decrypt permission. A 403 can conceal whether a key exists; a missing object may reflect lifecycle expiry or deletion. SQL references alone do not prove bytes remain.
