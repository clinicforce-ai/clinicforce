01 / orientation

Getting started

ClinicForce has a patient portal and a clinic workspace. A portal patient account and a clinic patient record are separate identities; the clinic can accept an insurance card from someone who has never created a portal account.

Reading the system

Choose a user action, find its screen, then follow the API adapter, route, service, and saved record. The operation list below gives exact request and response fields.

Running locally

Start PostgreSQL and HAPI with Docker Compose, provide an ignored local .env with the application database URL, run the backend, then run Vite. Vite forwards /api and /manifest to port 8000.

docker compose up -d
PYTHONPATH=backend python3 -m uvicorn app.main:app --reload
cd frontend && npm ci && npm run dev

Install backend/requirements.txt into a Python environment first. The backend loads the repository's ignored .env without replacing task-injected settings. The local Docker Compose database is for HAPI; the application also needs its own configured PostgreSQL connection.

Read-only documentation. Swagger has “Try it out” disabled on these pages. Inspect contracts here; use synthetic local data for mutation tests. Do not paste patient information, passwords, or payer credentials into a documentation viewer.

02 / request path

Architecture

Every feature crosses the same boundary: the browser collects intent, FastAPI decides what is allowed, and a store or integration carries out the work. A screen never writes directly to PostgreSQL, HAPI, or an insurer.

03 / user flow

Four complete user journeys

Use these routes as waypoints. The exact models, optional fields, and errors appear in the generated reference below.

Patient uploads a health PDF

PatientPortal → POST /api/patient/upload → PDF extraction → HAPI FHIR transaction → S3 or encrypted Drive → patient_documents. The database row holds filename, location, and extracted FHIR JSON; the original PDF stays in object storage.

Patient shares a clinician summary

POST /api/patient/generate-link creates a SMART Health Link and encrypted shl_manifests row. The clinician scans a QR, enters the PIN, then POST /api/doctor/decrypt-and-summarize builds the summary and report. Shares can expire or be revoked.

Clinic receives a card

Staff creates POST /api/staff/upload-links; patient sends a card through POST /api/insurance-upload/{clinic_code}/{upload_code}. S3 holds the image, while insurance_upload_links records the receipt and staff_intakes records the unconfirmed patient data.

Staff checks a visit

Staff confirms the clinic patient, opens an eCW appointment, selects a workflow, and reviews the result. V1 uses documents; V2 submits payer resources; commercial previsit combines eligibility evidence with verified clinic rates. Each writes a scoped case and stage history.

Worked card example

  1. Create. A clinic worker signs in, chooses a patient-specific link, and receives an expiring private URL. The token is stored as a hash in insurance_upload_links.
  2. Submit. Fictional patient Alex uploads two card images with consent. The server saves originals to S3, creates a staff_intakes row, marks the link received, and returns a receipt. The intake still needs identity confirmation.
  3. Review. Staff opens GET /api/staff/intakes/{intake_id}, optionally runs card OCR, and uses PUT /api/staff/intakes/{intake_id}/patient to confirm the clinic patient. field_sources distinguishes patient entry, OCR, and staff decisions.
  4. Check. Opening V2 creates insurance_cases.workflow_json and an intake workflow reference. A coverage submission saves submitting before the payer call; pending means wait or refresh, not confirmed benefits.

Follow a single record

insurance_upload_links.status = "received"
  └── intake_id → staff_intakes.id
       ├── fields / field_sources → submitted vs OCR vs confirmed facts
       ├── documents[*].object_key → private S3 original
       ├── patient_id → staff_patients.id after confirmation
       └── workflows.v2 or workflows["commercial:sha256(visit ID)"] → insurance_cases.id
            ├── workflow_json → case state and payer outcome
            └── insurance_case_events → stage and saved snapshot history

patients.patient_id is a portal identity; staff_patients.id is a clinic identity. Some relationships are checked by scoped application queries or JSON references rather than database foreign keys. A case row does not prove a payer answered: inspect the saved outcome, source, timestamp, and response reference.

05 / evidence to result

Insurance pipelines

The three insurance screens may look alike but make different claims. Keep the evidence type attached to every visible result.

PathInput → resultKey functions
V1 document reviewUploaded card, policy, fee and clinical documents → cited facts, requirements, staged review. No automatic proof of live payer eligibility.routers/insurance.py → v1_sources.py, documented.py, golden.py, store.py.
V2 payer transactionseCW appointment and confirmed services → coverage, referral, authorization, estimate or procedure-estimate request → submitting/pending/complete/error state.insurance_v2.py → ecw_backend.fetch_inputs(), availity.py, availity_results.py, store.save_v2().
Commercial previsiteCW visit → coverage candidate if needed → saved eCW or Stedi eligibility → rate match and benefit interpretation → estimate or review-required result.commercial_estimator.previsit_estimate() → stedi_discovery.py, stedi.py, commercial_store.py, visit_estimate.py.

Commercial visit, step by step

  1. Identify the visit. GET /api/doctor/insurance/commercial/appointments reads the clinic's eCW appointment context. Patient, appointment, coverage, provider, location, service date, and planned codes must be reconciled.
  2. Prepare the case. POST /appointments/readiness reports missing inputs. POST /appointments/previsit saves or reuses a case. Ambiguous discovery candidates stop the flow for staff review.
  3. Check coverage. An existing eCW eligibility result may be reused; otherwise configured Stedi may perform eligibility. A discovery search finds potential coverage, not a completed 270 eligibility check. An uncertain or pending request must not be blindly repeated.
  4. Price only with evidence. Match a verified payer connection, provider network, active rate version, CPT/HCPCS, place of service, and effective date. visit_estimate.price_lines() separates insured amount, conditional planning estimate, and cash option.
  5. Preserve history. insurance_cases.workflow_json stores working state; insurance_case_events.snapshot_json freezes eligible historical results. GET /commercial/history is eCW visit history; saved checks and later 835/financial reads are separate concepts.

Current environment boundary. At the October 3 deployment check, Availity was configured for demo and Stedi's commercial pilot switch was enabled. A configured switch does not establish a successful payer response for any patient. The API's configuration endpoints and each case outcome give the current workflow state.

Frontend libraries

React/React DOM render screens; TypeScript types adapters; Vite builds and proxies locally; Tailwind supplies utilities. Radix Dialog gives accessible dialogs; Lucide supplies SVG icons; Recharts draws clinical trends; html5-qrcode and jsQR read health-link QR codes; animejs supplies selected motion. The app uses handwritten API adapters, not a generated Swagger client.

Backend libraries and managed services

FastAPI, Pydantic, Uvicorn provide HTTP routing, validation, and serving. psycopg talks to PostgreSQL; httpx calls HAPI and outside APIs; boto3 uses S3, KMS, Bedrock, and related AWS services. PyMuPDF and local Tesseract read documents/cards; lxml parses XML/CCDA; jwcrypto and cryptography protect health links and Drive files; qrcode creates share images; Jinja2 and WeasyPrint render reports. Production tasks receive credentials from Secrets Manager; the browser never calls the payer with a secret.

Design and release plan

  1. Describe the actor, entry screen, permission, input, saved state, failure state, and next action before adding a route or table.
  2. Use an existing intake or case when its scope and lifecycle fit; introduce a table for a distinct access rule, version, query, or retention need. Keep original bytes out of application rows.
  3. Change a Pydantic model and its TypeScript adapter together. Add a focused test for the authorization or state transition that matters.
  4. Release through the application workflow: verify tests, build immutable images, preserve the deployed CloudFormation template and unrelated parameters, wait for ECS stability, publish static assets, then check live health and docs.

Do not infer a live integration from a route alone. On this verified deployment, Availity's environment was demo, ID.me was enabled in sandbox, and the Stedi commercial pilot switches were on. The production template source can differ from the currently deployed template if its last infrastructure update rolled back.

Keep the live guide current

Every new capability or change to a screen, workflow, API contract, data model, integration, infrastructure, deployment, or operational behavior must update the relevant section of this guide in the same release. Put the explanation where a reader would look for that topic, including setup, failure states, and operational checks when they matter. API contract changes also require accurate FastAPI route and model descriptions in the generated reference below. The guide source is backend/app/api/developer_docs.html; its OpenAPI grouping lives in backend/app/api/developer_docs.py. Infrastructure changes are documented here through a coordinated application release. Check the affected section on both Swagger and ReDoc after deployment. Keep patient data and secrets out of examples.

08 / investigation

Debug one request end to end

  1. Record the screen action, request URL/method, HTTP status, and a redacted correlation time. Never copy real patient or payer payloads into public notes.
  2. Find the wrapper in frontend/src/services/api/, then the matching FastAPI decorator. Check its session and practice/intake ownership path.
  3. Check the response's source and state. 200 may still mean pending, review_needed, or unavailable.
  4. Follow the store function, case revision, event snapshot, object key, or HAPI resource. Confirm which write committed before retrying a request that may have reached a payer.
  5. For a code change, update the Pydantic/TypeScript contract and one focused test for the state or data boundary that changed.

FastAPI's /healthz checks the HTTP process; /readyz checks the configured patient store. They are intentionally absent from OpenAPI. The reference below documents authenticated operations without making them public.

Trace an arrival estimate in CloudWatch

For eCW lookup, intake identity confirmation, and commercial previsit requests, copy the X-ClinicForce-Request-ID response header. Search that ID in CloudWatch log group /ecs/clinicforce-production-backend to join structured JSON events for the request. Events record stages, outcome and reason codes, opaque practice/intake/case identifiers, timing, and calculated amount in cents where applicable. A deferred or unavailable result must be investigated through its reason code and case evidence; it does not imply a payer supplied a price. The events deliberately omit names, dates of birth, request and response bodies, credentials, and raw payer data.
