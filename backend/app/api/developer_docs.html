    Start here

    ClinicForce connects a patient portal with a clinic workspace. Learn one journey first; you do not need to understand every integration on day one.

    Patient portal

    A person uploads records and chooses what to share with a clinician.

    Clinic workspace

    Staff receive insurance cards, confirm patient details and check visits.

    Two separate identities. A clinic patient can exist without a portal account. A portal login does not grant staff access.

    Orientation, learning path and source map

    ClinicForce has a patient portal and a clinic workspace. A portal patient account and a clinic patient record are separate identities; the clinic can accept an insurance card from someone who has never created a portal account.

    Reading the system

    Choose a user action, find its screen, then follow the API adapter, route, service, and saved record. The operation list below gives exact request and response fields.

    Running locally

    Start PostgreSQL and HAPI with Docker Compose, provide an ignored local .env with the application database URL, run the backend, then run Vite. Vite forwards /api and /manifest to port 8000.

    Follow the complete local setup for installation, databases, environment variables, staff login and exact startup commands. Then read which provider accounts to register, how to release through staging, and the worked eCW → Stedi estimate. For database rows and files, follow Query RDS and browse S3. Examples are synthetic. Source links point to the private GitHub repositories and require organization access.

    For future changes: start with this guide’s code map and the section for the workflow you are changing, then inspect its linked source and tests.     Browse publicly; execute with your main-app session. All APIs remain visible.     Try an API request

    Swagger is the interactive API reference below. Anyone can read it; running a request requires the matching patient or clinic login.

    Execute makes a real request. Use authorized test inputs. Clinic insurance operations may also require the intake ID from your workspace.

    Open API reference →
    Details and source links
    1. Open the main app on the same environment in another tab and sign in normally. Use the same scheme, host and port: for local Vite at http://localhost:5173, open http://localhost:5173/api/docs so mutation-origin checks match; production uses https://app.clinicforce.ai/api/docs. A clinic staff/admin login enables clinician operations; a portal patient login enables patient operations. A share-link/PIN session alone does not count as a clinic login.
    2. Return to /api/docs#reference and choose Refresh session. The status above the API viewer reports patient, clinician, both, signed out, or verification unavailable. All operations remain visible in every state; matching operations gain a Try it out button.
    3. Expand the operation, choose Try it out, fill the documented parameters/body, and select Execute. Browser cookies are sent automatically on the same origin; do not paste a cookie or provider bearer token into Swagger.
    4. For insurance endpoints requiring clinic context, enter the authorized intake ID in the field above the viewer. This sends X-ClinicForce-Intake; the server still checks clinic ownership, confirmed identity, case scope, staff/admin permissions and provider prerequisites. Swagger cannot inherit an intake selected only in another tab’s in-memory UI state.
    5. After signing out, switching accounts or signing in in the other tab, refresh the documentation. Every Execute also rechecks the live session; an expired or revoked login cannot continue executing from an old page. Clear entered values/results by reloading before sharing a screen.

    For patient operations that accept optional legacy patient_id/password fields, omit those fields when using the login cookie. A default Swagger example containing patient_id: "string" is not your identity and will fail the existing ownership check. Fill only the fields required by the operation; do not copy production credentials into example bodies.

    Patient paths require a patient session; staff and doctor paths require a clinic session. Other API operations require at least one of those logins. Both sessions can coexist and enable both groups. Routes outside /api/ remain reference-only in Swagger. Login/registration contracts are visible, but sign in through the main app to unlock execution. OAuth callbacks and token/share flows still need their own valid state and are usually completed through the main app rather than by manually executing callback URLs.

    Swagger uses a same-origin, no-store GET /api/docs/session probe that returns two booleans, not account or patient records. Each executed API request includes the non-sensitive __clinicforce_docs=1 query marker, which CloudFront already forwards. The server uses it for an additional matching-session gate, then runs the normal API authorization. It is not a credential and does not change which APIs are public outside Swagger. The public OpenAPI document is identical for all viewers and labels operations with x-clinicforce-session. Session-check failures lock execution; they do not silently enable it.

    Results and limitations: a 401 means sign in again; a 403 can indicate the wrong role, origin, clinic or resource ownership; a 422 means the required request shape/context is missing. Successful session verification does not make an unavailable eCW/Stedi integration work. POST/PUT/PATCH/DELETE requests can change real data, trigger emails or incur provider charges. Swagger is not a sandbox. Use staging and authorized representative cases; production access uses the same existing permissions as the app. The raw OpenAPI schema is available for API tools.

    Implementation: developer_docs.py, developer_docs.js, and application.py. Swagger UI is pinned to 5.32.0 because the operation-level selector is a plugin interface; re-run role/expiry/browser tests when upgrading. Learn the official Swagger configuration and plugin interfaces.
