01 / orientation

Getting started

ClinicForce has a patient portal and a clinic workspace. A portal patient account and a clinic patient record are separate identities; the clinic can accept an insurance card from someone who has never created a portal account.

Reading the system

Choose a user action, find its screen, then follow the API adapter, route, service, and saved record. The operation list below gives exact request and response fields.

Running locally

Start PostgreSQL and HAPI with Docker Compose, provide an ignored local .env with the application database URL, run the backend, then run Vite. Vite forwards /api and /manifest to port 8000.

Follow the complete local setup for installation, databases, environment variables, staff login and exact startup commands. Then read which provider accounts to register, how to release through staging, and the worked eCW → Stedi estimate. Examples are synthetic. Source links point to the private GitHub repositories and require organization access.

Read-only documentation. Swagger has “Try it out” disabled on these pages. Inspect contracts here; use synthetic local data for mutation tests. Do not paste patient information, passwords, or payer credentials into a documentation viewer.

Start here on a new computer. Commands use Bash on Ubuntu 24.04 or Ubuntu in WSL2. Register eCW and Stedi in this order

  1. eCW registration. Have the practice and integration owner register/activate the backend FHIR client for the authorized test practice. Record its issued backend client ID and exact issuer. Register the public JWKS URI accepted by eCW; ClinicForce serves the same public keys at /.well-known/jwks.json and /api/patient/ecw/jwks. Keep the private key server-side. The code signs RSA assertions with RS384 and a stable kid that must match the registered public key.
  2. Configure and verify eCW. In AWS, use the stack-managed signing key and its task permissions; set EcwBackendClientId and EcwBackendIssuer in the reviewed environment parameters. In an authorized local sandbox, set the equivalent uppercase env names. The current local-JWK helper additionally requires ECW_CLIENT_ID and OAuth state material (ECW_OAUTH_STATE_SECRET, falling back to EPIC_OAUTH_STATE_SECRET), even when the caller supplies a backend client ID. Coordinate those sandbox settings with the registration owner, or use the authorized sandbox KMS path. A private JWK alone is not sufficient. Verify a permitted Patient and Encounter result; token success alone is insufficient.
  3. Stedi account and routing. Create the designated test/integrated account in Stedi, provision a server API key, find the payer’s eligibility route, and complete any required enrollment for the actual test provider NPI. Follow Stedi’s current API/key instructions for test requests. API keys are not pasted into the React application.
  4. Store credentials and clinic configuration. Have the operator store the Stedi key in Secrets Manager and configure the approved StediApiKeySecretArn, or the supported managed-secret path. The default staging configuration has no such key. An externally managed secret must be readable by the execution role and use an accessible encryption key. Configure the clinic connection, network, profile and rates before enabling live checks. The optional STEDI_PRACTICE_API_KEYS map is supported in code; if present, an unmapped practice has no fallback key. The current shared template injects STEDI_API_KEY; a practice-key map requires an explicitly reviewed secrets-injection change.

Provider setup is an operator task with provider approvals, not a script that can generate working production entitlements. For learning, keep the local switches disabled and use the mocked checks in this guide. Inspect the live API reference for exact configuration models; do not invent an NPI, member ID, negotiated rate or enrollment status to make a real check pass.

Configure a connected test environment deliberately

For staging, edit clinicforce-aws/environments/staging.json with reviewed public parameters and secret ARNs, then follow the infrastructure release procedure. Do not paste secret values into a committed JSON file or terminal command. For local development, put authorized sandbox credentials only in the ignored env file and restart the API. A test eCW app must be activated for its test practice; a random name on a production issuer is still a production request. The scope tuple in ecw_backend.py is the executable list; confirm each grant with eCW, including optional evidence resources before relying on them.

For a usable commercial estimate, a clinic administrator must also configure a payer connection, verified provider/network mapping, estimate profile, and active rate version for the relevant service date, location, plan, CPT/HCPCS code, modifiers and units. These are database records, not API keys. Inspect GET /api/doctor/insurance/commercial/configuration in the API reference and the clinic configuration screens. The stored data lives in commercial_payer_connections, commercial_provider_networks, commercial_estimation_profiles and commercial_rate_*. A cash fee schedule does not substitute for a negotiated allowed rate. The V2 clinic allow-list is separate from commercial configuration.

For OAuth registrations, use https://staging.clinicforce.ai for authorized staging callbacks and https://app.clinicforce.ai for production. Do not repoint the production app to a laptop. Backend client-credentials lookup uses signed assertions and does not require a doctor to complete an OAuth redirect for each search. Learn the distinction in SMART Backend Services. Provider approval, enrollment and key registration happen in the provider’s administration process; there is no ClinicForce shell command that bypasses those prerequisites.

03 / user flow

Four complete user journeys

Use these routes as waypoints. The exact models, optional fields, and errors appear in the generated reference below.

Patient uploads a health PDF

PatientPortal → POST /api/patient/upload → PDF extraction → HAPI FHIR transaction → S3 or encrypted Drive → patient_documents. The database row holds filename, location, and extracted FHIR JSON; the original PDF stays in object storage.

Patient shares a clinician summary

POST /api/patient/generate-link creates a SMART Health Link and encrypted shl_manifests row. The clinician scans a QR, enters the PIN, then POST /api/doctor/decrypt-and-summarize builds the summary and report. Shares can expire or be revoked.

Clinic receives a card

Staff creates POST /api/staff/upload-links; patient sends a card through POST /api/insurance-upload/{clinic_code}/{upload_code}. S3 holds the image, while insurance_upload_links records the receipt and staff_intakes records the unconfirmed patient data.

Staff checks a visit

Staff confirms the clinic patient, opens an eCW appointment, selects a workflow, and reviews the result. V1 uses documents; V2 submits payer resources; commercial previsit combines eligibility evidence with verified clinic rates. Each writes a scoped case and stage history.

Worked card example

  1. Create. A clinic worker signs in, chooses a patient-specific link, and receives an expiring private URL. The token is stored as a hash in insurance_upload_links.
  2. Submit. Fictional patient Alex uploads two card images with consent. The server saves originals to S3, creates a staff_intakes row, marks the link received, and returns a receipt. The intake still needs identity confirmation.
  3. Review. Staff opens GET /api/staff/intakes/{intake_id}, optionally runs card OCR, and uses PUT /api/staff/intakes/{intake_id}/patient to confirm the clinic patient. field_sources distinguishes patient entry, OCR, and staff decisions.
  4. Check. Opening V2 creates insurance_cases.workflow_json and an intake workflow reference. A coverage submission saves submitting before the payer call; pending means wait or refresh, not confirmed benefits.

Commercial visit, step by step

  1. Identify the visit. GET /api/doctor/insurance/commercial/appointments reads the clinic's eCW appointment context. Patient, appointment, coverage, provider, location, service date, and planned codes must be reconciled.
  2. Prepare the case. POST /appointments/readiness reports missing inputs. POST /appointments/previsit saves or reuses a case. Ambiguous discovery candidates stop the flow for staff review.
  3. Check coverage. An existing eCW eligibility result may be reused; otherwise configured Stedi may perform eligibility. A discovery search finds potential coverage, not a completed 270 eligibility check. An uncertain or pending request must not be blindly repeated.
  4. Price only with evidence. Match a verified payer connection, provider network, active rate version, CPT/HCPCS, place of service, and effective date. visit_estimate.price_lines() separates insured amount, conditional planning estimate, and cash option.
  5. Preserve history. insurance_cases.workflow_json stores working state; insurance_case_events.snapshot_json freezes eligible historical results. GET /commercial/history is eCW visit history; saved checks and later 835/financial reads are separate concepts.

Unreadable cards and unavailable prices

Card files are saved before OCR. For a card embedded in a PDF page, the reader OCRs the original card image rather than the page header and surrounding whitespace. It enlarges small images, recognizes both labeled three-column cards and separately labeled subscriber/identification/group fields, and tries alternate local OCR layouts when the first pass misses identity or payer details. A card read has a 20-second request deadline; if it times out, the saved original remains available for retry and manual entry. Each proposed field retains page evidence. Staff must compare every proposed name, birth date, member ID, group, and payer to the original card; an empty or uncertain field stays for manual entry. Many printed cards do not include date of birth. A card alone does not prove eligibility. If the appointment or benefit request fails, the commercial screen shows Unavailable and the request error, with no insured advance calculated. Staff can retry the read, check the payer portal or call the payer, record the verification, and bill any final insured responsibility after adjudication. An arrival amount of $0.00 is shown only when a completed result supports it.

eCW lookup deadline

The staff patient lookup and commercial appointment list share an eCW reader. It limits metadata and backend authorization stages to 10 seconds each and the entire patient/appointment read to 24 seconds, ahead of CloudFront's 30-second origin read limit. On an upstream timeout, the API returns a retryable error instead of leaving the browser waiting for an edge 504. Timeout errors identify backend authorization, patient verification, or appointment search. The 24-second limit is ClinicForce’s request budget; reaching it alone does not establish an eCW outage or prove that a patient or appointment is absent. No appointment or eligibility result is inferred from a timed-out request. Use the response request ID and stage events described in the debugging section to distinguish a local deadline, transport failure, upstream HTTP rejection, and identity mismatch. Compare the request with the last working release before attributing an incident to an upstream service. Retry the read or review the saved card and verify benefits manually.

A configured switch does not establish a successful payer response for any patient. The API's configuration endpoints and each case outcome give the current workflow state.

Worked example: doctor → eCW → Stedi → estimate

This is a fictional teaching case, not a live patient or proof that a provider is available. Dr. Lee signs into the clinic workspace and enters Alex Example, born January 15, 1980. Suppose eCW returns one matching patient and a visit two days from today, and the clinic has one active, verified in-network policy and a reviewed rate for CPT 99213, one unit. For this example there is no usable saved eligibility, so a Stedi check is needed. Name and birth date alone cannot establish insurance benefits or a price.

FHIR is the JSON-based health-record format used by eCW and HAPI. An Encounter represents the visit used by this reader; Coverage describes a policy. Eligibility is commonly called a 270 inquiry / 271 response. Stedi’s JSON API carries the inquiry to the payer and returns benefits. A CPT/HCPCS code identifies a service; an NPI identifies a provider; the allowed amount is the clinic’s negotiated price. Learn FHIR R4 and Stedi eligibility.

Worked calculation: a synthetic $80 patient estimate

Assume one confirmed service, one active primary plan, individual benefits, verified in-network participation, no secondary coverage, no unresolved authorization/referral/identity issue, and a current clinic contract. The clinic rate is $200. The applicable remaining deductible is $50, coinsurance is 20%, the rule is coinsurance with no added copay, and remaining out-of-pocket allowance is $1,000. All are fictional inputs; missing terms must not be defaulted to these numbers.

Allowed amount:                      $200.00  (clinic contract)
Deductible applied: min($200, $50) =   $50.00  (payer benefit balance)
Amount after deductible:              $150.00
20% coinsurance on $150:                $30.00
Patient estimate: $50 + $30 =           $80.00
Plan estimate: $200 - $80 =            $120.00
Patient amount is capped by the allowed amount and remaining out-of-pocket limit.
Stored/calculated in integer cents: 20000, 5000, 3000, 8000, 12000.

Failure and recovery branches to understand

An eCW Patient timeout stops identity resolution: the staff API normally returns 502 with a request ID when the shared 24-second lookup deadline is reached; the staff route also has a 26-second outer bound. These bounds describe patient/appointment listing, not a guaranteed 24-second limit for the entire multi-stage previsit request. No appointment or Stedi result can be inferred from that failure. A completed query with zero appointments is different from a query that failed.

Missing payer/coverage identity can initiate background Stedi insurance discovery when required demographics/provider identity exist. Candidates are filtered against the patient. Automatic routing recovery is constrained to the same matching policy; a different/unresolved candidate requires staff review. The UI polls the saved case; it does not invent insurance. Explicit request-shape rejection may cause a bounded retry without optional identity hints; a self-subscriber AAA 73 name rejection may retry member ID plus DOB. A transport/parse failure after submission is indeterminate and must be reconciled against payer activity before another submission. See _post_stedi_eligibility, _begin_coverage_discovery and _start_previsit_recovery.

A successful benefit response with no matching contract rate still cannot establish a negotiated insured amount. Conflicting identity, multiple coverages, unknown network, service/date mismatch, or stale evidence can require review. The result may be HTTP 200 with issues, no price, or deferred collection guidance. A displayed $0 is meaningful only when completed evidence and calculation support it.

Locate a stalled eCW lookup

Under the same request ID, ecw_stage_started, ecw_stage_completed, and ecw_stage_failed describe metadata discovery, KMS assertion signing, token exchange, resource searches, and direct resource reads. Each event includes elapsed milliseconds, and an upstream HTTP status when one arrived. Resource requests include a fixed resource label, query shape such as given_family_birthdate (never values), page number, and returned count. Patient matching and appointment filtering record counts without identifiers. Failure codes distinguish connection/read/write/pool timeouts, upstream HTTP errors, invalid responses, resource denial, and cancellation. A cancellation followed by ecw_lookup_deadline means ClinicForce cancelled the in-flight stage at its overall budget; it is not an upstream HTTP 504. A missing upstream status means no complete HTTP response was available to the client. Commercial appointment-list requests also emit collection_http_completed, so their support references can be searched even when the reader fails.

fields @timestamp, event, stage, resource, query_kind, page, http_status, reason_code, duration_ms, count
| filter request_id = "SYNTHETIC-REQUEST-ID"
| sort @timestamp asc

To isolate a regression, compare the deployed eCW issuer/client/signing-key configuration and request shape with the last successful image. A diagnostic read may inspect a redacted FHIR OperationOutcome privately; never put raw response bodies, URLs, query values, bearer tokens, session cookies, or exception strings in application logs or this guide. A failure before patient and visit resolution prevents the Stedi estimate path from starting.
