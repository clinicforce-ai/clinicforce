    Start here

    ClinicForce connects a patient portal with a clinic workspace. Learn one journey first; you do not need to understand every integration on day one.

    Patient portal

    A person uploads records and chooses what to share with a clinician.

    Clinic workspace

    Staff receive insurance cards, confirm patient details and check visits.

    Two separate identities. A clinic patient can exist without a portal account. A portal login does not grant staff access.

    How a request works

    An API is how the screen asks the server to do something. The server checks permission, runs the rules and returns a result.

    Details and source links

    What users do

    Pick the journey closest to your task. Follow the action, the API request and the saved result.

    Upload a record

    Patient uploads a PDF → API extracts health data → original file is saved.

    Share a summary

    Patient creates a private link → clinician opens it with the PIN → summary appears.

    Send an insurance card

    Staff create an upload link → patient sends a card → staff review and confirm it.

    Check a visit

    Staff select a confirmed patient and visit → a workflow checks evidence → staff review the outcome.

    Details and source links

    Use these routes as waypoints. The exact models, optional fields, and errors appear in the generated reference below.

    Patient uploads a health PDF

    PatientPortal → POST /api/patient/upload → PDF extraction → HAPI FHIR transaction → S3 or encrypted Drive → patient_documents. The database row holds filename, location, and extracted FHIR JSON; the original PDF stays in object storage.

    Patient shares a clinician summary

    POST /api/patient/generate-link creates a SMART Health Link and encrypted shl_manifests row. The clinician scans a QR, enters the PIN, then POST /api/doctor/decrypt-and-summarize builds the summary and report. Shares can expire or be revoked.

    Clinic receives a card

    Staff creates POST /api/staff/upload-links; patient sends a card through POST /api/insurance-upload/{clinic_code}/{upload_code}. S3 holds the image, while insurance_upload_links records the receipt and staff_intakes records the unconfirmed patient data.

    Staff checks a visit

    Staff confirms the clinic patient, opens an eCW appointment, selects a workflow, and reviews the result. V1 uses documents; V2 submits payer resources; commercial previsit combines eligibility evidence with verified clinic rates. Each writes a scoped case and stage history.

    Worked card example
    1. Create. A clinic worker signs in, chooses a patient-specific link, and receives an expiring private URL. The token is stored as a hash in insurance_upload_links.
    2. Submit. Fictional patient Alex uploads two card images with consent. The server saves originals to S3, creates a staff_intakes row, marks the link received, and returns a receipt. The intake still needs identity confirmation.
    3. Review. Staff opens GET /api/staff/intakes/{intake_id}, optionally runs card OCR, and uses PUT /api/staff/intakes/{intake_id}/patient to confirm the clinic patient. field_sources distinguishes patient entry, OCR, and staff decisions.
    4. Check. Opening V2 creates insurance_cases.workflow_json and an intake workflow reference. A coverage submission saves submitting before the payer call; pending means wait or refresh, not confirmed benefits.
    eClinicalTouch / eClinicalMobile: QR to the patient chart

    Purpose. A patient shares a snapshot from ClinicForce with a clinician using the receiving EHR's SMART Health Link importer. ClinicForce calls its no-passcode option eClinicalMobile compatibility test. eClinicalTouch and eClinicalMobile are separate receiving apps; record the exact app, version, EHR build and enabled practice feature when verifying compatibility.

    What the vendor establishes. eClinicalWorks' April 9, 2026 production announcement describes scanning patient health QR codes with eClinicalMobile. Its official workflow demonstration shows the imported information as a PDF entry in PRISMA. The vendor's eClinicalTouch release history lists patient-shared SMART Health QR integration in version 4.19; the app requires EHR V12.0.2 or above. These sources establish the advertised workflow, not successful import of every ClinicForce resource or availability in every practice.

    1. Create the snapshot

    1. Sign in to the patient portal, review the records and complete legal given name, family name and birth date. ClinicForce requires matchable demographics and at least one clinical/document entry beyond the Patient resource.
    2. For ClinicForce's clinician viewer, choose standard sharing and a four-digit PIN. For a receiving mobile-EHR test, choose Generate eClinicalMobile test QR and acknowledge the no-passcode sharing notice.
    3. POST /api/patient/generate-link authenticates the patient, reconciles Drive deletions and assembles a FHIR R4 collection bundle. Sources are saved structured records, extracted facts and document metadata, plus a live Epic snapshot if a live Epic session is connected. Source tags preserve their origin.
    4. The server creates a random 256-bit key, encrypts the bundle as compact JWE using alg=dir and enc=A256GCM, and saves encrypted data, expiry and optional PIN hash in shl_manifests. The QR contains the key; the manifest response does not.
    ModeQR textAccess and destination
    standardhttps://app.clinicforce.ai/#shlink:/<encoded-payload>PIN-protected; opens the ClinicForce viewer. Payload includes flag: P.
    ecw_compatshlink:/<encoded-payload>Bare link, no PIN and no passcode flag. Intended for a compatible EHR importer. An ordinary phone camera may not handle this URI scheme.

    The encoded JSON contains v, url, key, label and exp. The actual production manifest address is https://app.clinicforce.ai/manifest/<opaque-token>; staging uses https://staging.clinicforce.ai/manifest/<opaque-token>. PUBLIC_BASE_URL controls the host. Default expiry is three hours (SHL_SHARE_TTL_SECONDS=10800). The QR image is not a PDF or the entire medical record. Anyone with a no-passcode QR has the capability to fetch and decrypt that snapshot before expiry; keep it out of screenshots, tickets and logs.

    2. Retrieve and decrypt after scanning

    A conforming receiver decodes the base64url JSON after shlink:/ (or extracts it from the viewer fragment), checks expiry and sends an HTTPS POST to its url. Opening the manifest URL with a browser GET is not this exchange. The receiving vendor may perform retrieval/decryption on a mobile device or a service behind it; its public demonstration does not specify that internal placement.

    // Synthetic receiver request body for ecw_compat; omit passcode
{"recipient":"Example receiving EHR","embeddedLengthMax":0}

// Standard shares also include the patient's PIN.
// The response contains one encrypted FHIR file:
{"files":[{"contentType":"application/fhir+json;fhirVersion=4.0.1",
            "location":"<temporary encrypted-payload URL>"}]}
// If embeddedLengthMax is omitted or large enough, "embedded" holds JWE instead.

    The manifest validates availability and, for standard shares, the PIN. Its recipient field is required but is not a provider login or identity verification. A size-limited receiver receives a presigned S3 URL and must GET that encrypted object before the URL expires (one hour by default). S3 URLs use AWS Signature Version 4, required for the KMS-encrypted object; an older S3 signature can return HTTP 400 even when manifest retrieval succeeded. The receiver then uses the QR key to authenticate/decrypt the JWE and parse FHIR. The original key never belongs in the manifest request body, query string or logs. Manifest expiry prevents new resolution; an already-issued object URL can remain usable until its own expiry, and previously retrieved data cannot be recalled.

    3. What “populate the chart” means

    The receiving EHR owns patient matching, authorization to modify its chart, duplicate handling, reconciliation and display. ClinicForce supplies demographics and FHIR resources; it does not issue a chart-write call to the practice in this QR route. A ClinicForce Patient ID is a portal identifier, not an eCW chart ID. Verify the selected/matched patient in the receiving workflow; do not invent an automatic match rule from names alone.

    Supported clinical FHIR resourcesAvailable conditions, medications, allergies, observations, procedures and other allowed resources, with source tags.Expected facts visible in the imported document. Structured medication/allergy/problem-list updates require separate evidence.
    DocumentReferenceMetadata about source documents. Exchange removes attachment bytes and storage URLs.The receiver cannot download original uploaded PDFs from this metadata. Do not confuse its imported/rendered document with a copied original PDF.

    Identity limitation in current compatibility code. apply_identity_assurance() adds IAL2/high-confidence labels and the IDI-Patient-L2 profile marker during compatibility assembly, without checking an ID.me verification result in this path. Those labels are implementation metadata, not proof of an identity-proofing event or validated profile conformance. They must not be used as evidence that the vendor's verified-identity prerequisite has been satisfied.

    The vendor demo establishes a document-import result. It does not establish automatic reconciliation into discrete EHR fields, exact supported FHIR profiles, trusted issuer/domain onboarding requirements, or ClinicForce-specific acceptance. The standard ClinicForce viewer's POST /api/doctor/decrypt-and-summarize and generated report are a separate workflow; the mobile importer does not need to call that endpoint.

    4. Verify each boundary and diagnose a failure

    1. Generation: verify authenticated generation returns the correct bare/wrapped format, host, expiry and PIN flag. Decode the PNG with an independent QR reader and compare its text to the returned SHL.
    2. Transport: resolve the manifest through CloudFront, test embedded and download-URL forms, decrypt with the QR key and verify expected FHIR content in memory. Check invalid PIN, unavailable share and malformed requests without printing payloads.
    3. Mobile import: record the app/version, EHR build and practice feature; scan a synthetic case with matching demographics. Confirm the intended chart, PRISMA document, expected facts and persistence after refresh. If discrete fields are required, verify them individually.
    4. Evidence: record only pass/fail, time, environment and support references. Research establishes vendor-documented behavior; a local conforming receiver establishes transport; only an observed receiving-app result establishes that installation's chart population.

    Generation failure: check authentication, demographics and source content. No edge request: check the scan feature, bare SHL support, device connectivity and log delivery delay. Edge error with no backend event: inspect CloudFront routing/origin result. Backend 422: request schema (including required recipient); 401: PIN; 404: unavailable/expired/revoked share; 503: encrypted-object storage. HTTP 200 with no imported document: investigate receiver decryption, FHIR acceptance, patient matching and importer configuration. A fetch success cannot certify chart population.

    Use QR and CloudFront diagnostics. Implementation: API routes, snapshot persistence, SHL/JWE encoding, exchange bundle, and patient QR controls.

    eCW patient suggestions and correcting saved identity

    A missing exact match does not prove that the entered details are wrong or that the patient is absent. The staff lookup returns 200 {status: "selection_required", candidates: [...]} with up to eight suggestions and Cache-Control: no-store. An empty list invites a refined search. Inexact or ambiguous eCW matches create no intake and read no encounters or benefits before selection. A conflicting saved clinic identity can also require confirmation after an exact eCW lookup; that lookup may already have read the verified eCW patient’s visits, but does not change the saved clinic identity. Provider authorization, transport and timeout failures remain errors rather than empty search results.

    The initial search uses the documented given/family/birthdate, family/birthdate and name/birthdate combinations. An ecw_account_number with DOB searches the secondary identifier and birth date, then verifies the returned secondary ACCT. First and last names can be blank, including for a patient ClinicForce has never linked. The returned name and DOB are shown for explicit staff selection before encounters are read or an intake is saved. ACCT without DOB returns 422; eCW does not support secondary-identifier-only search. The unsupported given+birthdate-only fallback is removed. For searches without an ACCT, bounded name-only fallback queries read only the first page (up to 100 rows per name); they never enumerate the practice roster. Suggestions are not exhaustive. Use a more precise name or the account number when the intended patient is not shown.

    First-name or surname suggestions permit one insertion, deletion, substitution or adjacent swap, with at least four normalized characters, exact DOB and the other name matching (including the existing compound-surname tail rule). Conflicting supplied middle initials exclude those suggestions. DOB differences require both names to match locally, or a verified exact account. An entered account excludes other accounts. Similarity only orders the dropdown; it never confirms identity. Ordered multiword given names are compared in full.

    The dropdown shows the eCW name, DOB and account, with differences from any supplied fields identified below it. Nothing is preselected, including ACCT-and-DOB results. Staff choose a patient and acknowledge identity before continuing. Changing selection clears acknowledgement; editing search fields, leaving the search or losing the session clears suggestions. The confirmation POST sends selected_patient_id, returned canonical demographics, displayed account when available and identity_confirmed: true. The server re-reads that ID and checks the demographics and account before reading encounters or saving; changed selections return 409. A similarity score is not a probability that two people are the same.

    New intakes retain eCW's canonical name. Explicit confirmation can update the linked ClinicForce patient's demographics only for the same eCW ID and practice; it records a staff event, clears prior insurance identity approvals if demographics changed and updates that intake's demographic source fields. A changed intake identity clears its prior portal association so corrected eCW demographics cannot inherit another portal identity. It never relinks an existing patient to a different eCW ID or rewrites saved insurance snapshots. A conflicting saved identity requires confirmation even when the new search itself is an exact match. Initial and saved-link checks apply the same surname rule, so a successfully matched compound surname does not fail solely because the saved display name used its final word.

    Commercial appointment listing and previsit reads return 409 with code: "ecw_patient_selection_required" for an unresolved eCW identity. The estimator offers Find matching eCW patients, opening the staff search with the saved details. Staff confirm a result before returning to its visits. Selecting another person opens that person's intake; the original patient and saved estimate stay attached to their original records. No payer request is made by suggestion search or confirmation.

    Failure and recovery branches to understand

    An eCW Patient timeout stops identity resolution: the staff API normally returns 502 with a request ID when the shared 24-second lookup deadline is reached; the staff route also has a 26-second outer bound. These bounds describe patient/appointment listing, not a guaranteed 24-second limit for the entire multi-stage previsit request. No appointment or Stedi result can be inferred from that failure. A completed query with zero appointments is different from a query that failed.

    Missing payer/coverage identity can initiate background Stedi insurance discovery when required demographics/provider identity exist. Candidates are filtered against the patient. A unique active medical policy matching the patient and a current or recorded prior address can recover missing or obsolete eCW policy details. Multiple active policies require reconciliation; discovery order does not establish primacy. The UI polls the saved case; it does not invent insurance. Explicit request-shape rejection may cause a bounded retry without optional identity hints; a self-subscriber AAA 73 name rejection may retry member ID plus DOB. A transport/parse failure after submission is indeterminate and must be reconciled against payer activity before another submission. See _post_stedi_eligibility, _begin_coverage_discovery and _start_previsit_recovery.

    A successful benefit response with no matching contract rate still cannot establish a negotiated insured amount. Conflicting identity, multiple coverages, unknown network, service/date mismatch, or stale evidence can require review. The result may be HTTP 200 with issues, no price, or deferred collection guidance. A displayed $0 requires a supported calculation; missing eligibility or secondary coverage alone cannot establish zero liability.

    Understand insurance results

    ClinicForce has three insurance workflows. Read the result according to the evidence that produced it.

    V1 · read documents

    Extract and review facts from uploaded files. This does not establish live eligibility.

    V2 · ask a payer

    Submit a transaction, then follow its pending, complete or error state.

    Commercial · estimate a visit

    Combine the visit, insurance benefits and verified clinic rates to calculate an estimate.

    Unavailable is not $0. Missing evidence or a failed request must stay visible. A saved case or insurance card alone does not prove coverage.

    Automatic coverage recovery and optional clearinghouses

    The normal route resolves the known payer and uses available subscriber/member details first. A known payer and explicit subscriber identity may be queried with demographics when the member ID is absent; payer requirements vary. That response must return matching patient identity and a usable subscriber ID. Missing policy/routing, rejected identity and inactive coverage enter bounded background recovery. No clinic-specific payer, identifier, benefit or price is invented.

    Appointment-note candidates. A uniquely labeled payer and subscriber number in eCW General Notes can supply missing inquiry hints even when Coverage is empty. Candidates are extracted before checking policy count; conflicting notes or multiple active policies do not select a primary policy. The original note source is retained. Notes never establish an active policy, a self relationship, policyholder demographics, benefits or an amount. No returned General Notes means no note candidate; ClinicForce does not infer one from clinical narrative or patient comments.

    Automatic member-ID recovery. No per-patient staff selection is required to finish recovery. First examine up to ten saved checks belonging to the same explicitly linked practice patient. One distinct policy can supply a candidate; current evidence is reused only with matching patient, provider, visit date, requested services, freshness and no newer eCW conflict. Older evidence requires a new eligibility check. Conflicting policies are never selected by recency. Saved case IDs and raw response references remain private.

    1. Read patient-bound ClinicForce cards or explicitly labeled eCW insurance cards through DocumentReference. ecw_scope_result records whether Coverage, DocumentReference and Binary read access was granted, without logging the token. Inline cards need only DocumentReference access; same-issuer Binary downloads obtain Binary access separately. Never forward credentials to other hosts or redirects. Up to two supported attachments are validated and read by the existing OCR pipeline. OCR supplies inquiry hints; only a matching payer response establishes benefits. Conflicting or unmatched card names cannot select a policy.

Patient demographics in an inquiry do not assert a self relationship; the returned patient, subscriber, identifier and active coverage must match before adoption. Normalize punctuation/case only; substantive identity differences require reconciliation. A missing eCW member ID is not required to recover a discovered ID.     Unreadable cards and unavailable prices

    Card files are saved before OCR. For a card embedded in a PDF page, the reader OCRs the original card image rather than the page header and surrounding whitespace. It enlarges small images, recognizes both labeled three-column cards and separately labeled subscriber/identification/group fields, and tries alternate local OCR layouts when the first pass misses identity or payer details. A card read has a 20-second request deadline; if it times out, the saved original remains available for retry and manual entry. Each proposed field retains page evidence. Staff must compare every proposed name, birth date, member ID, group, and payer to the original card; an empty or uncertain field stays for manual entry. Many printed cards do not include date of birth. A card alone does not prove eligibility. A failed refresh preserves the same visit’s previous result and labels it Previous estimate · needs recheck, with its saved time and the error. It is not presented as a newly verified collection amount. Changing the visit clears that result. An initial failure without a prior result offers a visit/benefit retry and retains the missing-input explanation. Staff can retry the read, check the payer portal or call the payer, record the verification, and bill any final insured responsibility after adjudication. An arrival amount of $0.00 requires a supported calculation from applicable benefits and rates.

    eCW lookup deadline

    The staff patient lookup and commercial appointment list share an eCW reader. It limits metadata and backend authorization stages to 10 seconds each and the entire patient/appointment read to 24 seconds, ahead of CloudFront's 30-second origin read limit. On an upstream timeout, the API returns a retryable error instead of leaving the browser waiting for an edge 504. Timeout errors identify backend authorization, patient verification, or appointment search. The 24-second limit is ClinicForce’s request budget; reaching it alone does not establish an eCW outage or prove that a patient or appointment is absent. No appointment or eligibility result is inferred from a timed-out request. Use the response request ID and stage events described in the debugging section to distinguish a local deadline, transport failure, upstream HTTP rejection, and identity mismatch. Compare the request with the last working release before attributing an incident to an upstream service. Retry the read or review the saved card and verify benefits manually.

    Details and source links

    This section explains the design implemented in this repository and the engineering reasons it supports. It is not a reconstructed meeting history: where no recorded decision exists, the rationale is an interpretation of the current code and constraints, not a claim that every alternative was evaluated. Current limitations are called out rather than presented as ideal design. Use the linked files to verify a decision before changing it.

    Browser → API → rules → stores

    Reason and behavior. The browser sends intent; the server validates identity, clinic scope, input and workflow state before accessing data or providers. Separating route contracts from insurance logic lets calculation rules be tested without a browser or real payer.

    Alternatives and tradeoffs. Direct browser-to-database/provider calls would distribute credentials and authorization into an untrusted client. A microservice for every layer would add deployment and network boundaries; the current single backend is simpler to coordinate, but shares scaling and failure capacity. Split services when independently measured load or ownership justifies that cost.

    Code to open: backend/app/api/application.py (route assembly), backend/app/api/routers/commercial_estimator.py (workflow orchestration), backend/app/insurance/visit_estimate.py (pricing rules).

    Same-origin sessions instead of browser-held provider tokens

    Reason and behavior. HttpOnly cookies let the app and Swagger reuse the same server-validated login without exposing session tokens to JavaScript. The backend holds eCW/Stedi credentials; mutation-origin checks complement cookie authentication.

    Alternatives and tradeoffs. Browser bearer tokens require their own storage/refresh and exposure controls. Cookies require careful CSRF/origin protection and environment isolation; HttpOnly does not make XSS harmless. Logging in to staging does not log you in to production. A share/PIN token is a separate resource grant, not a clinic account.

    Code to open: backend/app/api/services/authentication.py (patient checks), backend/app/api/routers/staff.py (clinic checks), frontend/src/services/api/client.ts (same-origin requests).

    Public API reference, login required to execute

    Reason and behavior. Readers can inspect every contract without an account. Swagger enables matching patient or clinician operations only after main-app sign-in, and checks the session again before execution. A server-side Swagger marker gate rejects missing/wrong sessions; the actual route still checks ownership and permissions.

    Alternatives and tradeoffs. A completely read-only viewer prevented useful authenticated testing. A separate developer login would duplicate identity management. Swagger now performs real writes and potentially paid provider calls: use authorized test inputs in staging. Removing the Swagger marker does not grant access to a protected API; it restores that route’s normal public/authenticated contract.

    Code to open: backend/app/api/developer_docs.py (audience metadata and server gate), backend/app/api/developer_docs.js (browser session checks and intake context).

    Separate portal and clinic patient identities

    Reason and behavior. A clinic can receive a card and confirm a patient who has never registered for the portal. Practice-owned staff_patients and staff_intakes therefore differ from portal patients and their sessions. eCW identity matching is an explicit reconciliation step.

    Alternatives and tradeoffs. One shared patient ID would simplify joins but incorrectly equate portal registration, clinic ownership and an external EHR identifier. Separation needs explicit links and identity confirmation; name/DOB ambiguity cannot be solved by choosing the first search hit.

    Code to open: backend/app/core/staff_store.py (clinic identities), backend/app/core/patient_store.py (portal identities), backend/app/insurance/ecw_backend.py (external identity checks).

    PostgreSQL rows, S3 files, HAPI FHIR

    Reason and behavior. Relational rows support accounts, ownership, case state, joins and rate versions. S3 holds original documents and raw response evidence, with rows keeping references. HAPI provides a FHIR resource interface instead of making every caller implement a FHIR server.

    Alternatives and tradeoffs. Putting all bytes in PostgreSQL expands backups and mixes file delivery with row queries. Using only object storage makes transactional relationships harder. These stores are not one atomic transaction: missing objects and orphan cleanup need explicit handling. Cloud HAPI and application tables currently share one database and role, reducing isolation; separate databases/roles would strengthen that boundary at additional operational cost.

    Code to open: backend/app/core/patient_store.py (row schemas), backend/app/core/object_store.py (object keys and encryption), backend/app/ingestion/fhir_client.py (FHIR client).

    eCW supplies visit context; Stedi supplies payer evidence

    Reason and behavior. The eCW reader resolves patient identity and visit/coverage/provider context. Stedi eligibility/discovery is a distinct payer interaction. Clinic rate tables and benefit interpretation then produce an estimate; a successful eligibility response alone does not contain a guaranteed patient price.

    Alternatives and tradeoffs. A single “insurance result” abstraction would hide whether a fact came from the EHR, payer or clinic. Explicit evidence/source/time and identity checks require more reconciliation but avoid treating unknown coverage as zero cost. Revisit an adapter when a provider contract changes, preserving source provenance and failure states.

    Persist pending state and reuse qualifying evidence

    Reason and behavior. The workflow saves submission state before a payer request and retains case/event/evidence records. Matching previously obtained evidence can avoid repeat calls, but patient, practice, payer, dates and workflow context must qualify it. Events retain historical snapshots alongside mutable current state.

    Alternatives and tradeoffs. Always calling the payer increases latency, cost and duplicate-submission risk; caching indefinitely can return stale or unrelated evidence. A timeout does not prove the remote action failed. There is no claim of an atomic transaction spanning PostgreSQL, S3 and the payer, or universal exactly-once delivery. Inspect saved state before retrying.

    Code to open: backend/app/api/routers/commercial_estimator.py (submission ordering), backend/app/insurance/store.py (cases and events), backend/app/insurance/commercial_store.py (evidence reuse).

    Bounded synchronous eCW lookup

    Reason and behavior. The staff interaction waits for the reader with a 24-second overall budget and a 26-second outer route deadline, ahead of CloudFront’s 30-second origin read timeout. This permits an application error and support reference rather than an edge-generated HTML timeout.

    Alternatives and tradeoffs. Longer waits cannot repair an unresponsive upstream and may exceed the edge deadline. A background job/polling design could support longer work but needs job identity, status storage, cancellation, deduplication and a different UI. Current failure is explicit: no patient/appointment absence or successful estimate is inferred from a timeout.

    Code to open: backend/app/insurance/ecw_backend.py (reader deadlines), backend/app/api/routers/staff.py (route deadline).

    Managed AWS services with explicit network boundaries

    Reason and behavior. CloudFront serves cached static assets and routes API requests to ALB/ECS Fargate. RDS is private; object buckets block public access. Fargate removes host management while security groups restrict service-to-service ingress.

    Alternatives and tradeoffs. EC2 would require host patching/capacity management. Kubernetes would add orchestration overhead for this small service set. The current design is not maximum isolation or availability: tasks use public subnets/IPs for outbound access, no NAT is declared, service desired counts are one, and some internal hops use HTTP. Private compute, internal TLS and multiple tasks are improvements to assess against availability/security needs and cost—not assumed existing protections.

    Code to open: stacks/clinicforce-production.yaml; see the deployed topology and storage map.

    KMS signing and separate credential storage

    Reason and behavior. An asymmetric KMS key signs eCW app assertions without exporting the private key. Secrets Manager supplies server credentials at task startup; the browser receives neither provider secrets nor signing keys.

    Alternatives and tradeoffs. A private key file is easier locally but creates key-distribution and rotation obligations in production. KMS adds IAM permissions, network dependency and signing latency. Injected secrets are not automatically refreshed in a running task; rotation requires task replacement where configured.

    Code to open: backend/app/ingestion/ecw.py (assertion signing), backend/app/insurance/ecw_backend.py (token exchange).

    Build once, stage, then promote exact artifacts

    Reason and behavior. CI checks source, builds image digests/frontend bytes, deploys staging and verifies that artifact. Production promotion reuses those exact bytes so the released code is the code tested in staging. Application and infrastructure repositories keep image releases separate from resource provisioning.

    Alternatives and tradeoffs. Rebuilding for production can resolve different dependencies or base images. Direct local uploads lose provenance. Artifact reuse depends on retention, compatible database changes and preserved image digests; rollback is not a database restore. Two repositories also mean coordinating stack updates and documentation explicitly.

    Code to open: .github/workflows/deploy.yml (CI/CD jobs), scripts/check_release.py (provenance checks), scripts/release.py (artifact deployment).

    Structured request diagnostics without payload logging

    Reason and behavior. Request IDs and fixed stage/resource labels correlate browser errors with upstream timing and application outcomes. CloudWatch stores events; CloudTrail records AWS actions such as signing. Patient values, credentials and raw provider bodies are excluded from the structured diagnostic events.

    Alternatives and tradeoffs. Dumping complete requests is easier for ad hoc debugging but exposes sensitive data. Reduced logs cannot reveal eCW’s internal cause or reproduce patient data; private source-system investigation may still be needed. Audit current legacy logging separately instead of assuming every log stream follows the structured schema.

    Code to open: backend/app/logs/collection_audit.py (safe event fields), backend/app/api/application.py (request correlation), backend/app/insurance/ecw_backend.py (upstream stages).

Record the UTC time, method/path, status and X-ClinicForce-Request-ID response header (also shown as a support reference). Do not export a HAR or copy cookies/payloads: those can contain credentials and patient data. Each HTTP request has its own ID, so patient lookup, identity confirmation, appointment listing and previsit may have different IDs.

    Open the CloudWatch Logs Insights console in us-east-1.        outcome, reason_code, http_status, duration_ms, count,
       status, basis, amount_cents, case_id, revision
| filter request_id = "00000000-0000-4000-8000-000000000001"
| sort @timestamp asc
| limit 200

    Replace the synthetic ID with the response header. A collection_http_completed event exists for the instrumented lookup, identity, appointment-list and previsit routes, not every API operation.     2. Read the fields, not just the red error line
    Field / eventMeaning
    event, stageWhat happened and where: metadata, assertion_signing, token_exchange, resource_search, patient_identity or appointment_search. Stage starts without a corresponding completion narrow the area to inspect.
    resource, query_kind, pageSafe labels such as patient, given_family_birthdate, and page 1. They identify query shape without revealing the name/DOB or full URL.
    http_statusIn an eCW stage this is the upstream HTTP status, if a complete response arrived. In collection_http_completed it is ClinicForce’s response. Missing upstream status is not a 200 or proof of an upstream 504.
    duration_msMilliseconds spent in that stage/request. 24000 means 24 seconds. Nested stage durations overlap; do not add all rows as if they were independent.
    reason_codeClassification: read_timeout, connect_timeout, upstream_http_error, invalid_response, cancelled, lookup_deadline, no_match, etc. It is not raw upstream exception text.
    ecw_patient_match, ecw_appointments_selectedIdentity and visit selection counts. A completed match with count 1 differs from a failed search with no count. Count zero after an upstream timeout must not be interpreted as a completed no-results search.
    eligibility_requested / received / rejected / indeterminateSubmission started, usable response arrived, explicit rejection was received, or outcome is unknown. Inspect saved case state/evidence before repeating any potentially paid transaction.
    collection_calculated, collection_savedThe result’s status, basis, amount_cents and saved revision. Persistence is not proof that a payer supplied an allowed price. Missing amount is different from zero.
    collection_http_completedEnd of an instrumented HTTP request. An HTTP 200 can contain deferred/review/unavailable workflow state, so read its preceding events and case result.

    QR sharing: CloudFront edge logs and backend correlation

    Start with the UTC time and X-ClinicForce-Request-ID response header from generation or manifest retrieval. CloudFront's X-Amz-Cf-Id identifies the edge request; the backend copies that value into cloudfront_request_id. These are different IDs. Each HTTP call gets its own IDs; they do not join generation and a later scan automatically, and they are not patient/share identifiers.

    Edge destination. CloudFront standard logging v2 delivers JSON to clinicforce-staging-cloudfront or clinicforce-production-cloudfront in CloudWatch Logs, us-east-1, with 30-day retention. The infrastructure output CloudFrontLogGroupName identifies the destination. Logging covers the distribution; filter the static cache pattern /manifest/* for QR retrieval. /api/* includes generation and other API calls and cannot identify generation alone at the edge.

    The selected edge fields are date/time, edge location, HTTP method/status, edge request ID, result/response/detailed-result types, total time, first-byte time and cache-behavior path pattern. URI paths, query strings, cookies, referrers, user agents, client IPs, headers and bodies are excluded. In particular, the manifest token is a secret capability and must never be added as cs-uri-stem. QR fragments and encryption keys are not HTTP request targets.

    // Logs Insights: select the environment's CloudFront group
fields @timestamp, `cs-method`, `sc-status`, `x-edge-request-id`,
       `x-edge-result-type`, `x-edge-detailed-result-type`, `time-taken`
| filter `cache-behavior-path-pattern` = "/manifest/*"
| sort @timestamp desc
| limit 100

    Backend destination. Select /ecs/clinicforce-staging-backend or /ecs/clinicforce-production-backend. Structured sharing_http_completed events use stages share_create, manifest_fetch and share_summary, recording status, duration, outcome, request ID and edge ID when present. Validation failures are captured even if the route body never runs. sharing_http_failed means an unhandled exception before a normal response. Sharing responses include Cache-Control: no-store. Access logs redact the manifest path token and query.

    fields @timestamp, event, stage, request_id, cloudfront_request_id,
       http_status, outcome, duration_ms
| filter event in ["sharing_http_completed", "sharing_http_failed"]
| sort @timestamp desc
| limit 100

// To join one edge request, add this filter to the backend query:
// | filter cloudfront_request_id = "EDGE_REQUEST_ID_FROM_CLOUDFRONT"

    The existing Secure Sharing messages additionally identify successful creation mode, manifest attempt, invalid PIN, unavailable share and lifetime PIN lockout. They do not carry a durable share-to-import receipt. No QR key, PIN, patient values, recipient label, encrypted payload, manifest token or download URL belongs in these diagnostics.

    Timing and limits. Standard logs are asynchronous and best effort. AWS documents that configuration changes can take up to 12 hours. Wait for actual delivered test events before declaring edge logging verified; an enabled setting or empty immediate query is insufficient. An S3 download and the receiver's chart write are separate from a manifest 200. This configuration does not add S3 object-access auditing or vendor mobile logs. New logging is not retroactive. Charges follow CloudWatch vended-log ingestion, storage and query usage.

Check delivered JSON contains only the approved fields. Promote the same verified artifacts, then repeat the affected checks in production using only an authorized case.     Staging and production releases

    The release pipeline uses clinicforce-staging at https://staging.clinicforce.ai and clinicforce-production at https://app.clinicforce.ai. Each stack owns its VPC, ECS services, RDS database, document and static buckets, keys, secrets, and log groups. Staging starts empty with a synthetic QA staff account. Never copy production databases, documents, patient identities, or provider credentials into staging. Its Stedi fixture mode makes no paid eligibility requests; eCW is unconfigured until a separately authorized test connection exists.

Production is a manual promotion of that successful staging run.     Details and source links
    1. Open the main app on the same environment in another tab and sign in normally. Use the same scheme, host and port: for local Vite at http://localhost:5173, open http://localhost:5173/api/docs so mutation-origin checks match; production uses https://app.clinicforce.ai/api/docs. A clinic staff/admin login enables clinician operations; a portal patient login enables patient operations. A share-link/PIN session alone does not count as a clinic login.
    2. Return to /api/docs#reference and choose Refresh session. The status above the API viewer reports patient, clinician, both, signed out, or verification unavailable. All operations remain visible in every state; matching operations gain a Try it out button.
    3. Expand the operation, choose Try it out, fill the documented parameters/body, and select Execute. Browser cookies are sent automatically on the same origin; do not paste a cookie or provider bearer token into Swagger.
    4. For insurance endpoints requiring clinic context, enter the authorized intake ID in the field above the viewer. This sends X-ClinicForce-Intake; the server still checks clinic ownership, confirmed identity, case scope, staff/admin permissions and provider prerequisites. Swagger cannot inherit an intake selected only in another tab’s in-memory UI state.
    5. After signing out, switching accounts or signing in in the other tab, refresh the documentation. Every Execute also rechecks the live session; an expired or revoked login cannot continue executing from an old page. Clear entered values/results by reloading before sharing a screen.

    For patient operations that accept optional legacy patient_id/password fields, omit those fields when using the login cookie. A default Swagger example containing patient_id: "string" is not your identity and will fail the existing ownership check. Fill only the fields required by the operation; do not copy production credentials into example bodies.

    Patient paths require a patient session; staff and doctor paths require a clinic session. Other API operations require at least one of those logins. Both sessions can coexist and enable both groups. Routes outside /api/ remain reference-only in Swagger. Login/registration contracts are visible, but sign in through the main app to unlock execution. OAuth callbacks and token/share flows still need their own valid state and are usually completed through the main app rather than by manually executing callback URLs.

    Swagger uses a same-origin, no-store GET /api/docs/session probe that returns two booleans, not account or patient records. Each executed API request includes the non-sensitive __clinicforce_docs=1 query marker, which CloudFront already forwards. The server uses it for an additional matching-session gate, then runs the normal API authorization. It is not a credential and does not change which APIs are public outside Swagger. The public OpenAPI document is identical for all viewers and labels operations with x-clinicforce-session. Session-check failures lock execution; they do not silently enable it.

    Results and limitations: a 401 means sign in again; a 403 can indicate the wrong role, origin, clinic or resource ownership; a 422 means the required request shape/context is missing. Successful session verification does not make an unavailable eCW/Stedi integration work. POST/PUT/PATCH/DELETE requests can change real data, trigger emails or incur provider charges. Swagger is not a sandbox. Use staging and authorized representative cases; production access uses the same existing permissions as the app. The raw OpenAPI schema is available for API tools.
